# Governance, Configuration, and Change Hunting

#### When to use this file

Reach for this file when the target lets people or programs change how plant software is configured or who may act in it: settings stores, tag and asset mappings, site templates, approval and management-of-change workflows, role and account administration, remote-support access, offline update and backup tooling, license and certificate handling, and security-event logging. The important path is *configuration or authority change → stored setting → value, record, or permission that people rely on*. Use `RECORDS-AUDIT-AND-SIGNATURES.md` for audit trails, signatures, record release, and attribution inside a record, `OT-BOUNDARY-AND-CONTROL-WRITES.md` for write allowlists, write-relaxing modes, and what a remote-access path can reach in the control zone, `ALARMS-HMI-AND-DISPLAY.md` for how stale or missing data renders, `DATA-ISOLATION-AND-LIFECYCLE.md` for generic tenant isolation and restore authority, `SUPPLY-CHAIN-AND-RELEASE.md` for generic signing and update metadata, `CLOUD-AND-DEPLOYMENT.md` for deployment configuration precedence, `WEB-PROTOCOL-AND-AUTH.md` for authentication mechanics, and `DESKTOP-MOBILE-AND-LOCAL-IPC.md` for local credential stores. Classes here produce both finding kinds: authority and approval bypasses are `security`; configuration or change paths that silently produce wrong plant data or records are `data_integrity`.

Split large targets by configuration store, approval workflow, account and access administration, site and template management, update and backup tooling, and event logging.

## Core discipline (include in every agent prompt for this domain)

```
- A change control that lives only in the UI, a written procedure, or a document is not a control. Find the server-side check that runs on every path that writes the setting: API, admin endpoint, import, file watcher, migration, startup, and sync.
- Take the expected behavior from the software's own code, schema, settings, and shipped documentation: its roles, approval steps, separated duties, change gates, and site scopes. Do not import a standard's requirement as the expected behavior, and never report a missing policy document.
- Approval, signature, and audit identity is the authenticated principal's stable ID. Track it through shared logins, service accounts, delegation, impersonation, and support sessions; display names, role labels, and client fields are not identity.
- Configuration is plant data when it changes what a value means: tag mappings, scaling, engineering units, time zones, site assignment, alarm limits, and write allowlists. A wrong or stale setting that reaches a screen or record is `data_integrity`; a change applied by an actor without the authority is `security`.
- Never apply a configuration change, update package, restore, license change, or support-access toggle to a live or shared system. Reproduce with in-repo fixtures, dummy principals, and a fixture clock inside the sandbox.
- Use `confirmed` for a source-complete path from writer to applied effect plus bounded local evidence of the result. Use `needs_validation` when OS file permissions, installer behavior, directory-service policy, a remote-access gateway, or the site's monitoring pipeline outside the repository decides the outcome.
```

## Configuration and change-control attack classes (subagent_type: `general`)

**Out-of-band configuration change paths**
A setting that the software puts under change control in its UI can also be changed by editing a file, setting an environment variable, calling an admin or debug API, dropping a file into a hot-reload directory, or running a migration or seed script, and the change takes effect with no record, approval, or version. List every writer of each controlled setting (tag mappings, scaling and units, alarm limits, write allowlists, roles, site assignment) and compare the authorization, versioning, and audit record each writer produces with the strongest path. Check file watchers and reload handlers, startup code that overwrites stored settings from files or environment, and migrations that rewrite configuration rows. Use `RECORDS-AUDIT-AND-SIGNATURES.md#Unaudited write paths` for audited records and `OT-BOUNDARY-AND-CONTROL-WRITES.md#Writable-point allowlist matching and ownership gaps` for how the write allowlist matches; a change by someone who already holds host administrator or service-account rights is not a finding unless the software claims to record such changes or a lower-trust user can reach the path.

**Management-of-change gate enforcement gaps**
The software says a change needs an approved management-of-change record before it applies, but the server never checks the record, checks it only in the client, or checks a record that does not bind the change actually applied. Find the server-side handler that applies the change and verify that it loads the record, requires an approved state, and compares the record's scope (asset, tag, setting, value, time window, authorization requirements) with the normalized change. Check alternate paths that apply the same change without the gate: bulk import, API clients, site sync, retries, and scheduled activation after the approval window closes or the record is withdrawn. A record linked after the fact is a finding only when the software states that the record gates the change.

**Site template and mapping copy drift**
One template, tag mapping, unit configuration, or asset model is copied to another site, unit, or environment and carries values that are wrong there: source-site tag paths, scaling, engineering units, time zone, shift calendar, alarm limits, or connection targets. Trace the copy or clone function and list which fields are rewritten, which are copied verbatim, and which keep a live reference to the source template. Check what happens when the template later changes: whether updates silently overwrite local overrides, skip some sites, or leave copies at an older version with no visible version marker. Report `data_integrity` only when a copied value reaches a screen, record, or calculation for the new site with nothing that shows it came from elsewhere.

**Test and simulation settings in production builds**
A production build or default install ships a simulator connector, a demo or replay data source, seeded test accounts, fixed approval or signature bypasses, or a test-mode flag that a site setting can switch on. Diff build profiles, packaging scripts, installer defaults, and seed data against the test fixtures, and trace whether a simulated or replayed source can feed the same screens, records, and calculations as a live source without a visible marker. Verify that test-mode branches in approval, signature, and write paths are compiled out or fail closed in production. Use `OT-BOUNDARY-AND-CONTROL-WRITES.md#Bypass, maintenance, and simulation mode leakage` for modes that relax write controls and `CLOUD-AND-DEPLOYMENT.md` for development values that disable authentication or transport security; a simulator that the product clearly labels and that cannot reach production records is not a defect.

## Authority, separation, and account attack classes (subagent_type: `general`)

**Change self-approval and role-combination gaps**
The software states that a requester cannot approve their own configuration, mapping, access, or management-of-change request, or that two administrative roles must be held by different people, but the check compares display names, emails, or role labels instead of stable principal IDs, or is missing on some path. Check each approval handler for a requester-versus-approver comparison on the stable ID, and test edits after approval that change the object while the approval stays attached. Check role assignment for combinations the software says are separated, including a user who grants themselves the second role, two accounts the software itself links to one person, and a group membership that confers both. Use `RECORDS-AUDIT-AND-SIGNATURES.md#Release sequencing and separation-of-duties bypass` for batch, lot, and result release; a deployment that allows one person both roles through a documented setting is not a finding, but a separation enforced on one path and not another is.

**Delegated and impersonated authority carryover**
Delegation, acting-as, impersonation, or support sign-in lets one person act with another approver's authority, and the resulting approval or record names only the original approver, outlives the delegation, or exceeds the delegated scope. Trace how a delegated session is created, which principal the authorization check uses, which principal the audit record and signature manifestation name, and when the delegation expires or is revoked. Check whether an impersonating administrator can sign or approve as the impersonated user, and whether queued or scheduled actions keep running under a revoked delegation. Report authority used beyond the delegation's scope or life as `security`, and use `RECORDS-AUDIT-AND-SIGNATURES.md#Shared-account and proxy-identity attribution loss` when the only defect is which person the record names.

**Shared, service, and break-glass account lifecycle gaps**
Generic operator logins, service accounts, integration keys, and emergency break-glass accounts can change configuration, grant access, or approve changes, and the software never expires or disables them, allows interactive use of accounts meant for programs, or never records that they were used. Find each non-personal account in seed data, installers, and account code, then check whether it allows interactive login, whether actions under it reach approval or role-administration steps, and whether rotation, expiry, and disable are enforced on the server. Check break-glass enabling for a time bound, an automatic disable, and a record of who enabled it, when, and what was done under it. Use `RECORDS-AUDIT-AND-SIGNATURES.md#Shared-account and proxy-identity attribution loss` for which person a record names and `OT-BOUNDARY-AND-CONTROL-WRITES.md` for break-glass modes that relax write controls; a shared read-only viewing account that cannot create or change records is not a defect.

**Remote-support and vendor access lifecycle gaps**
Vendor or remote-support access to the application can be enabled without the approval the software states, by the vendor itself, or by a role that should only request it, and the vendor account, support grant, or support mode stays enabled with no end time or record. Read the code that requests, approves, enables, and ends support access and creates vendor accounts, and check who may approve, whether the approver must differ from the requester, whether an end time is enforced on the server, and whether the tokens and keys issued are revoked at the end. Check whether support mode widens roles, skips approval steps, or survives a restart, update, or restore, and whether enable, each privileged action, and disable are recorded. Use `OT-BOUNDARY-AND-CONTROL-WRITES.md#Remote-access reach beyond the named control-zone asset` for what a tunnel or session can reach; access governed entirely by a remote-access gateway outside the repository is `needs_validation`.

**Site identifier trust in multi-site deployments**
One deployment serves several sites or units, and the site that scopes a read, write, approval, or configuration change comes from a client field, request header, message payload, topic or tag-path prefix, or a gateway's self-reported name rather than the authenticated principal's site grants. Trace the site identifier from each entry point to the query, write allowlist, and approval check, and test whether a dummy user granted one site can read data, approve changes, or alter configuration at another by changing that field. Check site-scoped roles that are applied plant-wide and cross-site dashboards or reports that skip per-site checks. Values filed under the wrong site because a gateway's reported name is trusted are `data_integrity` when they reach that site's screens or records. Use `DATA-ISOLATION-AND-LIFECYCLE.md` for generic tenant classes; report here only the site, unit, and gateway identity angle.

## Update, inventory, and recovery attack classes (subagent_type: `general`)

**Asset inventory and SBOM claim gaps**
The software claims to produce a component inventory or SBOM, but the build does not generate it, generates it from a manifest that omits bundled, vendored, statically linked, or installer-added components, or reports versions that differ from what ships. Compare the generation step with the packaged artifact: lockfiles, vendored directories, bundled runtimes, native drivers, protocol stacks, and installer payloads. For an asset inventory built from discovery, check that devices and versions are recorded as reported, stale entries are marked, and distinct devices that share a name or address are not merged. Report `data_integrity`, with the inventory as the record and the artifact or device as the source; the absence of an SBOM the software never claims is not a finding.

**Offline and air-gapped update acceptance gaps**
The update path for disconnected sites (removable media, file share, manual upload, or a relay server) accepts a package without the signature, product, or version checks the online path applies, or accepts a downgrade to an older version. Compare the online and offline update handlers side by side and verify that both check the signature, trust root, product, platform, and version order before any file is written or any install script runs. Check whether a package can carry its own trust root or key, whether a failed signature or revocation check falls back to install when no network is reachable, and whether a rollback is accepted without an explicit, recorded authorization. Use `SUPPLY-CHAIN-AND-RELEASE.md` for generic signing and update metadata; report here only the offline and downgrade paths.

**Configuration backup and restore resurrection**
Restoring a configuration backup brings back revoked accounts, withdrawn write allowlists or approvals, retired tag mappings, or old alarm limits, and the restore leaves no record of what changed. Trace the restore handler and compare the restored set with current state for accounts, roles, credentials, write allowlists, mappings, and site assignments, and check whether revocations made after the backup are reapplied. Verify that the restore itself requires authorization and writes an audit record listing what it changed, and check restores of one site's backup into another site. Use `DATA-ISOLATION-AND-LIFECYCLE.md#Restore reintroduces invalid state` for generic restore authority and `RECORDS-AUDIT-AND-SIGNATURES.md#Restore and archive trail loss` for records and their trails; a restore that reports every change and requires the same approval as a direct change is not a defect.

**License, certificate, and subscription expiry that stops data silently**
An expired license, certificate, subscription, or trial stops collection, display updates, calculations, or alarm evaluation, while screens keep showing the last values as current with good quality and no expiry state. Find the license and certificate checks in collectors, connectors, calculation jobs, and alarm engines, and trace what each returns on expiry: a swallowed exception, an empty result rendered as no change, or a skipped loop that leaves the last value in place. Check whether the expiry state reaches the screen, the record, and the data quality field, and whether data missing during the gap is marked missing rather than interpolated. Use `ALARMS-HMI-AND-DISPLAY.md` for how a stale value renders once collection stops and `WEB-PROTOCOL-AND-AUTH.md` for certificate failures that fall back to weaker authentication; a stop that shows a clear expired or not-collecting state is intended behavior.

## Secrets and security-event attack classes (subagent_type: `general`)

**Default and fleet-shared credentials**
Installers, images, templates, or seed scripts ship fixed passwords, API keys, signing keys, or broker and database credentials that are the same at every site, and the software does not force a change before use. Search installers, container images, seed data, configuration templates, and connector defaults for literal credentials and keys, and check whether first start generates per-installation secrets or refuses to run with defaults. Check whether one site's key can authenticate to another site, sign another site's records, or decrypt another site's backups. A placeholder that blocks startup until replaced is not a defect.

**Plain-text secrets on shared plant workstations**
Credentials for historians, brokers, databases, OPC UA servers, or the software's own service are stored in plain configuration files, registry values, or scripts that every local user on a shared plant PC can read. Find where each secret is written, read the file or key permissions the installer or code sets, and compare the secret's authority with that of the local users who can read it, such as an operator account on a shared console. Check logs, crash dumps, exported diagnostics, and support bundles for the same secrets. Use `DESKTOP-MOBILE-AND-LOCAL-IPC.md` for generic credential stores; a secret readable only by the service account and administrators is not a finding, and permissions set outside the repository are `needs_validation`.

**Security-event emission and forwarding loss**
Failed logins, permission and role changes, configuration changes, approval and signature events, or support access are never emitted, or are dropped before they reach the site's monitoring, while the software says it records or forwards them. Map the software's own event catalog, audit settings, or forwarder configuration to the code paths that should emit each event, and find paths that change the same state without emitting it. Trace the forwarder for drops on queue overflow, connection loss, filters, log rotation, and swallowed exceptions, and check whether a drop is itself recorded and visible. Report `security` when an actor can trigger the loss to hide an action and `data_integrity` when an ordinary condition loses an event the software claims to keep. Use `RECORDS-AUDIT-AND-SIGNATURES.md` for the audit trail of records; an event the software never claims to produce is a missing feature.

## Universal moves (apply across the above)

- For each setting that changes plant data or authority, list every writer: UI, API, admin CLI, file on disk, environment variable, import, restore, migration, site sync, and vendor tool. Compare the authorization, version, and audit record on each with the strongest writer.
- For each approval or signature, record the requester's stable ID, the approver's stable ID, the normalized object approved, and the object applied. Compare them across direct, bulk, queued, retried, scheduled, imported, and restored paths.
- Walk the lifecycle of every non-personal account, delegation, and support grant: create, use, expire, revoke, back up, and restore. A grant that survives any step it should not is the candidate.
- Render the shipped configuration for each build profile, installer default, and site template, diff them, and trace one value from template to site to screen or record.

## Validation rules (apply before reporting ANY finding here)

1. Name the actor or ordinary plant condition, the configuration or change path, the control the software states, the path that skips it, and the result: an unauthorized change applied, or a wrong value or record reaching a named consumer.
2. Cite the software's own statement of the control in code, schema, settings, or shipped documentation. A control the software never claims, a missing policy document, or a deviation from a standard alone is not a finding.
3. For authority claims, show with dummy principals that the actor cannot make the change through the normal path and that the alternate path accepts it. An actor who already holds host administrator or service-account rights crosses no boundary unless the software claims to record or block that change.
4. For data-integrity claims, trace the setting to the value or record and show that the consumer cannot see the difference: the value still shows current and good, or the record names the wrong person, site, or version.
5. Reproduce expiry, update, restore, and support-access behavior only with fixture clocks, packages, backups, and accounts inside the sandbox. Any lead that touches safety instrumented systems or interlocks is `needs_validation`, with the safety system's owner named in the blocker.
6. Return `confirmed` only with a source-complete path from writer to applied effect and the observed wrong result or unauthorized change. Return `needs_validation` with the exact OS permission, installer, directory-service, remote-access gateway, monitoring pipeline, or site-deployment fact required.
