# Alarm, HMI, and Display Hunting

#### When to use this file

Reach for this file when the target renders plant data for people: operator and engineering screens, HMI pages, dashboards, trends, tooltips, reports, exports, alarm lists and banners, and alarm notifications sent by email, SMS, push, chat, or webhook. The important data path is *source value with its quality, time, unit, and provenance → store, cache, and API → renderer or notification → the person who reads it*. Most classes here produce `data_integrity` findings, where what a person sees differs from what the data says. Authorization gaps on shelving, suppression, out-of-service, and acknowledgement, and notification content that reaches the wrong audience, produce `security` findings. Use `PROCESS-DATA-INTEGRITY.md` for value and timestamp corruption that happens before the display layer, `CLIENT-SIDE.md` for DOM rendering and XSS, `DATA-ISOLATION-AND-LIFECYCLE.md` for cross-user and cross-site cache keys, and `PROTOCOLS-RPC-AND-MESSAGING.md` for message delivery semantics.

Split large targets by surface: live screens, trends, alarm lists and alarm state actions, exports and reports, health indicators, and notifications.

## Core discipline (include in every agent prompt for this domain)

```
- A display finding needs a source state and a rendered state that differ on a named surface: screen, trend, tooltip, export, report, or notification. Name the role that reads it and the wrong state that role would conclude.
- Quality, freshness, unit, and provenance are part of the value. Trace each field from the decoder to every renderer; the defect usually sits where a DTO, serializer, cache, chart adapter, or message template drops or defaults it.
- Loading, error, empty, disconnected, and stale are states. Compare how each one renders against a good current value before deciding anything renders correctly.
- Shelving, suppression, out-of-service, and acknowledgement are state changes with authority. Name the actor, the check, the audit entry, the expiry, and the scope on every path that makes the change.
- Read alarm and acknowledgement forwarding from source; never send an acknowledgement, shelve, reset, or command to a control system or simulator. Alarms that come from a safety instrumented system are out of scope: report such leads as `needs_validation` with the safety system's owner named.
- Style preferences and practices a standard merely recommends are not findings. Use `confirmed` only when source evidence and a bounded fixture render show a wrong state reaching the surface; use `needs_validation` when the decisive fact is a renderer, chart library, provider, or control-system behavior absent from the repository.
```

## Value state and freshness attack classes (subagent_type: `general`)

**Quality and status rendering loss**
A value whose source quality is bad or uncertain, such as an OPC UA StatusCode with Bad or Uncertain severity or a Sparkplug metric marked STALE, reaches a screen, trend, tooltip, or export styled exactly like a good value. Trace the quality field from the decoder through every DTO, store, cache, websocket message, and chart adapter, and find where it is dropped, defaulted to good, or collapsed into a boolean that loses the uncertain case. Check that a bad value, which the source says must be ignored, is not replaced on screen by zero, a stale number, or the previous point. Quality carried only by color is a finding where color does not survive, such as CSV and PDF exports, printouts, text notifications, and screen-reader output, or where the same color also means a normal state elsewhere on the surface.

**Last-known value presented as live**
After a disconnect, session loss, Sparkplug NDEATH, subscription failure, or gateway restart, the display keeps showing the last value as current, often beside a timestamp that keeps advancing. Check what the client store does when the stream closes or a heartbeat lapses: whether values are marked stale, and whether the time shown is the sample time or the time the client last re-rendered or polled. Check reconnect paths that replay a cached value or a retained MQTT message and stamp it with receipt time as though it were a new sample. Verify that source signals such as Bad_NoCommunication, Uncertain_LastUsableValue, and a host marking metrics STALE on NDEATH each reach the screen. A value that genuinely has not changed is not a defect when the connection is healthy and its sample time is shown.

**Loading, error, and empty states rendered as normal**
A pending request, failed query, timeout, permission denial, or empty result renders as zero, as a blank field the reader takes as normal, as a flat trend line, as an empty alarm list, or as an "all clear" or "no active alarms" banner. Read each component's loading and error branches, default props, placeholder values, and null coalescing such as `?? 0` or `|| 0`, and read the API handlers that return an empty list or a success status after a backend failure. Render "no alarms exist", "alarm query failed", and "not yet loaded" from fixtures and compare the output; if any two are indistinguishable to the reader, the finding stands. A labelled spinner, an error banner, or explicit "unavailable" text is not a defect.

**Modeled values styled as measurements**
Predictions, forecasts, soft-sensor estimates, model or simulation output, interpolated or gap-filled points, manual entries, and overridden values appear in the same style, list, tag picker, table column, or export field as instrument measurements. Trace the provenance field from the producing model, calculation, or entry form to each renderer, and check whether trends, tables, tooltips, search results, and exports keep it. Check whether an overridden value that the source reports with good severity, such as OPC UA Good_LocalOverride, is shown as an override or only as good. A modeled value labelled as an estimate on the surface where it is read is not a defect; the finding is a label lost on some surface, merge, overlay, or export.

## Units, time, and number presentation attack classes (subagent_type: `general`)

**Units, time zone, and sample-time omission**
A screen, trend axis, tooltip, export, report, or notification shows a value without its unit, with a unit taken from the wrong tag or a stale configuration, or with a time whose zone or meaning (sample time, server receipt time, ingestion time) is not stated. Trace engineering units from source metadata such as OPC UA EUInformation into each renderer, and check the fallback when the unit is absent or reported as unavailable, when a tag's unit changes, and when a conversion is applied without relabelling. Check every time rendering for zone conversion, daylight-saving transitions, and whether a server or receipt timestamp is presented as the sample time. A unit or zone stated once in the surface header, and correct for every value on that surface, is not a defect.

**Rounding, truncation, and sign distortion**
Display formatting changes the meaning of a value: a small concentration rounds to zero, a value just past a limit rounds onto the limit, a value and its limit are rounded to different precisions so they appear equal or reversed, a negative sign is dropped or clipped, or a large value is truncated by a fixed-width field. Read the format functions, fixed-decimal and significant-figure settings, locale decimal separators, percent conversions, clamp-to-range logic, and the handling of censored results such as below-detection-limit markers in tables, tiles, gauges, exports, and notifications. Compare each formatted string with the stored value at the boundary cases using fixtures. A precision choice that no shown comparison, limit, or decision depends on is not a finding.

**Trend scaling, gap, and downsampling distortion**
A trend hides a change the data contains or draws a change the data does not contain. Check autoscale that flattens a meaningful excursion against one outlier or stretches sensor noise into an apparent swing, and fixed ranges that clip values off the axis without a marker. Check whether missing data, bad-quality points, and communication gaps are drawn as connected lines or held flat instead of as breaks, and whether stepped series are drawn interpolated or the reverse. Trace server and client downsampling, such as averaging, decimation, and bucket sampling, to verify that each bucket keeps its minimum and maximum or that the reduction is labelled, so a spike or dip is not dropped. Autoscale on a visible axis is not a defect by itself; the finding is a feature present in the data and absent from the rendered points, or the reverse.

**Mixed time-base trend alignment**
Series on one trend, table, or export use different time bases, such as source time and server receipt time, UTC and local time, lab sample time and result-entry time, or batch-relative and wall-clock time, and are aligned as if they shared one. Check how each series' timestamps are chosen, converted, and joined, including index-based alignment, nearest-neighbor joins with no tolerance, and series shifted by a daylight-saving offset. Reproduce with fixture series whose correct alignment is known and compare the rendered alignment. Timestamps already wrong before they reach the display layer belong in `PROCESS-DATA-INTEGRITY.md`.

## Alarm state and handling attack classes (subagent_type: `general`)

**Shelving, suppression, and out-of-service authorization gaps**
An alarm can be shelved, suppressed, or placed out of service by a principal without the authority, with no audit entry, or with no expiry, so it stays hidden from the people who need it. Find every path that changes these states, including UI actions, API routes, bulk or select-all actions, imports, scheduled jobs, and mobile clients, and compare the role check, site or area scoping, reason capture, and audit write on each. Verify that a shelve carries an expiry the server enforces rather than a client timer, and that expiry, unshelve, and return to service also write audit entries. Verify that bulk shelving checks authority on each alarm rather than once for the batch, and that the active-alarm view shows how many alarms are hidden. Suppression by design configured by an engineer is not a finding unless a lower-authority principal can change it or the product conceals its effect.

**Acknowledgement scope and source confusion**
An acknowledgement made in the software is shown as, or forwarded as, acknowledgement at the control system, or a control-system acknowledgement is shown as acknowledged by a named software user. Check which system holds the authoritative alarm state, which fields record who acknowledged, where, and when, and whether the screen distinguishes local acknowledgement from upstream acknowledgement. Check that an acknowledgement binds to the alarm instance the user saw, so it cannot acknowledge a later occurrence, a changed priority, or another site's alarm through a broad identifier, and that acknowledging requires the role the product says it requires. Treat the mismatch between systems as `data_integrity` and acknowledgement without authority as `security`.

**Flood and chatter masking of distinct alarms**
Flood, chatter, or grouping logic hides the first alarm in a sequence, or hides a distinct new alarm among repeats of an older one. Read the grouping keys, collapse rules, sort order, page limits, and "N more" truncation, and check whether a new condition on the same tag, a priority change, or a different alarm type merges into an existing row. Check whether first-out order survives events that arrive out of order or are sorted by receipt time rather than event time, and whether a list cut at a page limit says so. Grouping that keeps a visible count and lets the reader expand to each distinct alarm is not a defect.

**Alarm and notification deduplication collapse**
A new alarm or notification is dropped because its deduplication key matches an earlier one. Read the key construction and window: a key on tag alone, on message text, or on a rounded value, or one without site, condition, or occurrence identity, collides distinct events, and a window that resets on each repeat can suppress a condition indefinitely. Check what happens to a return to normal followed by a new activation inside the window, and whether dropped events are counted anywhere a person reads. Suppressing genuine redelivery of the same event is intended; delivery-level idempotency belongs in `PROTOCOLS-RPC-AND-MESSAGING.md`.

## Health, delivery, and caching attack classes (subagent_type: `general`)

**Self-silencing monitoring and health indicators**
A "source down", "monitoring stopped", or "data stale" warning is raised by the same process, connection, or thread whose failure it reports, so the failure also silences the warning; or a health indicator reports healthy while its own checks are failing. Check where heartbeats and watchdogs run, which component writes the health status, and whether a status record keeps its last good value after the checker stops. Check whether a failed, timed-out, or crashed check is caught and recorded as success, and whether the display treats an absent or expired health record as healthy. A narrow health check that states honestly what it checks is not a defect.

**Silent notification delivery failure**
An alarm notification by email, SMS, push, chat, or webhook fails at enqueue, at the provider, or under a rate limit, and nothing a person reads records that it never arrived. Read the send path for swallowed exceptions, fire-and-forget calls, status set to sent at enqueue rather than on provider acceptance, bounded queues that drop when full, retry loops that give up without a record, and rate limiters that discard rather than defer. Check whether a failure reaches the alarm record, an administrator view, or a fallback channel. What a provider does after accepting a message is outside the repository, so that part of a candidate is `needs_validation`.

**Notification and lock-screen content disclosure**
Notification titles, bodies, email subjects, SMS text, push payloads, and lock-screen previews carry process values, tag names, site names, or alarm text to people or devices outside the intended audience. Check how recipients are resolved at send time, and whether removed users, users of other sites, and stale distribution lists still receive messages. Check whether push payloads carry full content where a reference would do, and whether a sensitive-content or lock-screen setting the product offers is actually applied. Compare the data in each notification with what the recipient could read in the product under their current role. Content the recipient is entitled to read is not a disclosure merely because it appears on a lock screen, unless the product promises to hide it there.

**Dashboard and report cache age concealment**
A cached dashboard, tile, report, export, or API response serves old data without showing its age, so a reader takes it as current. Read the server caches, CDN configuration in the repository, service-worker caches, client stores, and precomputed report tables, and check whether the generated-at time travels with each cached payload and reaches the screen. Check refresh failure: a cache that keeps serving after its refresh job fails, with no age shown, is a stronger candidate than one that is merely slow. Where the code reads a source with an OPC UA maxAge, the server returns its best-effort value rather than an error when it cannot meet that age, so verify the code compares the returned ServerTimestamp against the age it asked for. Cache keys that omit user, role, or site belong in `DATA-ISOLATION-AND-LIFECYCLE.md`.

## Universal moves (apply across the above)

- Build a state matrix per surface: render good, uncertain, bad, stale, disconnected, loading, error, empty, overridden, and modeled fixtures through each screen, trend, tooltip, export, and notification template, and mark every pair of states that renders identically.
- Follow one value field by field from the source decoder to every sink, listing which of value, quality, sample time, unit, and provenance each hop carries. The first hop that drops a field is the root cause.
- Compare the UI, API, bulk, scheduled, import, and mobile paths for every alarm state change and every notification send. The weakest path sets the finding.
- Exercise the edges with fixtures only: daylight-saving transitions, UTC against local time, data gaps, zero, negative and very small values, values at a limit, and reconnect after a dropped stream.

## Validation rules (apply before reporting ANY finding here)

1. Name the source value with its quality, time, unit, and provenance; each transformation; the surface; the reading role; the decision that surface informs; and the exact difference between source and rendered state.
2. Show the difference is invisible on the surface where the decision is made, or flagged there in a way that states the wrong thing. A cue visible on that same surface clears the candidate; a cue only on a separate diagnostics page does not.
3. For trend and formatting claims, cite the chart configuration or format function and show the data points or strings it produces from a fixture. Where the decisive behavior lives in a chart library or renderer outside the repository, mark the candidate `needs_validation`.
4. For shelving, suppression, out-of-service, and acknowledgement claims, cite every route and handler that changes the state and show, with dummy principals in a local test, which one skips the check, audit write, or expiry. Control-system acknowledgement semantics outside the repository go to `needs_validation` with the control-system owner named.
5. For notification and health claims, cite the failure branch and the status it records, and show that no surface a person reads reports the failure. Provider, push-service, and device behavior outside the repository go to `needs_validation`.
6. Return `confirmed` only with the complete source-to-surface trace and a fixture render or local test showing the wrong state reaching the named surface. Return `needs_validation` with the exact renderer, library, provider, control-system, or deployment fact required and a bounded local or owner-observed check that would settle it.
