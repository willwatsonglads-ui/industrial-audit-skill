# Industrial Protocol and Device Hunting

#### When to use this file

Reach for this file when the target speaks an industrial protocol as client, server, publisher, subscriber, or gateway: OPC UA client and server stacks, MQTT and Sparkplug B edge nodes and host applications, Modbus and other fieldbus drivers, protocol-translating gateways, historian interfaces, and the device or gateway configuration surfaces the software embeds or drives. The triggering data path is lower-trust input, peer, or network position → protocol session or message → write, command, method call, history change, configuration change, or impersonated identity. Classes here produce `security` findings. Use `PROCESS-DATA-INTEGRITY.md` for protocol-handling defects that only corrupt a value, timestamp, quality, or identity on its way to a consumer, `OT-BOUNDARY-AND-CONTROL-WRITES.md` for write approval, writable-point allowlists, mode changes, and downloads toward the control side, `GOVERNANCE-CONFIGURATION-AND-CHANGE.md` for default credentials and configuration change, `PROTOCOLS-RPC-AND-MESSAGING.md` for generic broker topic ACLs and peer-to-principal binding, `WEB-PROTOCOL-AND-AUTH.md` for mTLS and certificate lifecycle, `MEMORY-SAFETY-AND-BINARY.md` for decoder memory safety, and `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` for availability impact.

Split large targets by protocol, by client, server, and gateway role, and by read, write, command, and administration path.

## Core discipline (include in every agent prompt for this domain)

```
- Never connect to a live plant network, controller, gateway, historian, broker, OPC UA server, or field device, even read-only. Prove paths from source and from fixtures, simulators, and in-memory brokers the repository ships, on isolated loopback, and send no write, command, method call, or rebirth beyond the single dummy message that shows a path exists.
- Name the identity at every hop: end user, application service account, OPC UA application instance certificate and session user token, MQTT client id and broker credential, Sparkplug group_id and edge_node_id, and the identity a gateway uses downstream. Show where the end user's authority is checked before the protocol operation.
- Protocol attributes describe authority; they do not enforce the application's. UserAccessLevel and UserExecutable reflect the session's user, Sparkplug topic segments are text any permitted publisher can write, and the base Modbus application protocol defines no authentication at all.
- A disabled security setting is a finding only when a lower-trust user, peer, or network position reaches a concrete outcome through it: a write, command, method call, configuration change, credential, or impersonated identity. Insecure settings confined to a loopback-only test fixture are not findings.
- Report only the security outcome here. A defect whose only result is a wrong, stale, or mislabelled value goes to `PROCESS-DATA-INTEGRITY.md`, and any lead that touches a safety instrumented system or interlock is `needs_validation` with the safety system's owner named.
- Use `confirmed` when source shows the path from lower-trust input or peer to the protocol operation and a bounded unit test, fixture, or repository simulator shows the request formed or the forged message accepted. Use `needs_validation` when server endpoint configuration, trust-list contents, broker ACLs, bridge configuration, gateway or device behavior, or network reachability lies outside the repository.
```

## OPC UA channel and session trust attack classes (subagent_type: `general`)

**OPC UA security mode and policy downgrade**
A client or server the repository configures selects or accepts MessageSecurityMode None, or a SecurityPolicy the stack or project marks deprecated or weak, on a channel that carries credentials, writes, or method calls. Read endpoint definitions, client endpoint-selection code, configuration defaults, and environment flags. Check whether the client takes the first or least secure endpoint a server lists, retries with None after a secure connection fails, or lets a request parameter or source record choose the mode. Mode None applies no security to messages, and OPC UA requires the None profile to be disabled by default, so compare shipped defaults with that. A None endpoint confined to a loopback test fixture, or one carrying no credential, write, or method call and only data the deployment treats as public, is not a finding.

**OPC UA certificate trust and identity binding gaps**
Certificate validation is disabled, wired to an auto-accept callback, or reduced to a chain check, so any peer certificate opens a session, or a lower-trust user can move a certificate into the trust list. Find the validation callback and every flag that skips it, then trace who can write the trusted-certificate store: directory permissions the repository sets, an upload or "trust this server" endpoint, a UI action, promotion of a rejected certificate, or trust-on-first-use. Compare the application URI and host names in the peer certificate with the endpoint URL and the application description the session claims, and check whether a mismatch only logs a warning. Defer revocation, renewal, and expiry fallback to `WEB-PROTOCOL-AND-AUTH.md`; an audited trust action restricted to administrators is intended authority, not a defect.

**OPC UA user token and session identity weakness**
An endpoint the software hosts offers an Anonymous or weak user token policy for operations that need a named user, or a client authenticates every end user's work with one shared username, certificate, or issued token. Read the user token policies per endpoint, the identity-validation callback, and the role or permission mapping that turns a token into authority. Check that a callback that throws or returns nothing does not fall through to Anonymous, that usernames are checked against a real store rather than a hard-coded or empty-password default, and that an identity changed through ActivateSession on an existing session re-runs authorization. On the client side, find where the user token is chosen and whether an end user's request can select another configured identity. Anonymous browse or read of data the deployment treats as public is not a finding by itself.

**Discovery, endpoint, and reverse-connect trust confusion**
The client trusts what a discovery response, endpoint list, or inbound reverse connection tells it, using a peer-supplied endpoint URL, certificate, security mode, or server identity without comparing it with configured expectations. Check whether endpoint URLs returned by discovery send the client and its credentials to a host the configuration does not name, and whether a stored server certificate or application URI is pinned and compared on every connect. For reverse connect, check whether the listener accepts sessions from any server, maps them to a configured connection by a peer-supplied URI, or binds beyond the interface the configuration names. Confirm that the substituted peer receives a credential, reaches a write path, or has its data attributed to another server; a discovery result that only selects among configured servers, each fully validated, is not a defect.

## Write, command, and gateway authority attack classes (subagent_type: `general`)

**Write and method authority checked against the wrong identity**
The application lets an end user write a node, call a method, or send a command through a protocol session that authenticates as a service account, and relies on that session's attributes instead of checking the end user's own authority. AccessLevel ignores user rights, and UserAccessLevel and UserExecutable reflect only the session's user, so a client that gates writes on either, or on an attribute cached under a broader identity, grants the end user the service account's authority. Trace each write, method call, and command handler from request to protocol call and find the per-user, per-node, per-operation check. Compare the node, method, and argument object that was authorized with the one sent. Defer allowlist matching to `OT-BOUNDARY-AND-CONTROL-WRITES.md` "Writable-point allowlist matching and ownership gaps"; report here the identity confusion itself. Server-side rejection under a correctly scoped per-user session prevents confirmation.

**Hosted address-space and method overexposure**
An OPC UA server, Sparkplug edge node, or Modbus server that the software itself hosts exposes writable nodes, callable methods, or command metrics to a lower-trust client, and those map onto application configuration, credentials, file paths, scripts, or downstream device writes. Enumerate the nodes, methods, and command handlers the repository registers, the roles or permissions assigned to each, and the handler each one reaches. Check method input arguments for path, query, script, and URL sinks, and confirm that the Executable, UserExecutable, and role permissions the server reports match what the handler enforces. A read-only address space exposing only data the deployment treats as public is not a finding.

**Unauthenticated fieldbus write reachability**
An application input reaches a Modbus or other unauthenticated fieldbus write, so anyone who can call that input can change a coil or register; the base Modbus application protocol defines no authentication or authorization of its own. Trace the function code, unit identifier, address, quantity, and values from the request to the driver call, and check whether a read endpoint accepts a caller-chosen function code. Verify that an allowlist blocking Write Single Coil (05), Write Single Register (06), Write Multiple Coils (15), and Write Multiple Registers (16) also blocks Write File Record (21), Mask Write Register (22), and Read/Write Multiple Registers (23), and that address ranges are checked after offset and unit-identifier translation. Stop at the formed request frame in a unit test or repository simulator, and use `OT-BOUNDARY-AND-CONTROL-WRITES.md` "Read-only claim and latent write-path gaps" when the software claims to be read-only. A write path restricted to an authenticated, authorized administrator with an audited per-request record is intended authority.

**Protocol gateway identity and authorization loss**
A component that translates between protocols, such as REST or MQTT to OPC UA, OPC UA to Modbus, or one broker to another, accepts a request under one identity and forwards it under its own, losing the caller and the authorization decision on the way. For each translation, record the inbound identity, the outbound identity, where inbound principals are mapped to allowed nodes, registers, topics, or commands, and whether retries, batch requests, and alternate inbound protocols pass the same check. Check that a bridge does not widen scope, for example by forwarding a whole topic tree, command topics included, from a lower-trust broker into a higher-trust one. Defer generic peer-to-principal binding to `PROTOCOLS-RPC-AND-MESSAGING.md` and writes into a system that a control-side consumer polls to `OT-BOUNDARY-AND-CONTROL-WRITES.md` "Indirect write-down through an intermediate system"; report here only a translated operation that reaches a device, server, or broker with authority the caller lacked.

## MQTT and Sparkplug B attack classes (subagent_type: `general`)

**Sparkplug command and rebirth reachability**
A lower-trust producer, application user, or bridged broker can publish NCMD or DCMD messages, including a 'Node Control/Rebirth' request, to edge nodes it should not command, or the application builds a command topic and metric from request fields. Every NBIRTH carries a 'Node Control/Rebirth' metric, and a rebirth request makes the node stop sending data and republish its full birth sequence, so treat it as a command, not a read. Trace every path that publishes on a command topic, the group_id and edge_node_id it uses, the metric names and values it accepts from input, and the per-user check before publish; where the repository ships broker ACLs, compare which clients may publish there. This class covers who can reach the command topic; whether the application gates a command like a write belongs to `OT-BOUNDARY-AND-CONTROL-WRITES.md` "Mode-change and command-method exposure", generic producer trust to `PROTOCOLS-RPC-AND-MESSAGING.md` "Untrusted producer treated as control plane", and rebirth floods to `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md`. A host application requesting rebirth after its own reorder timeout expires is specified behavior, not a defect.

**Sparkplug edge identity, birth, and death spoofing**
The host application takes edge node or device identity from the topic path or payload alone, so any client allowed to publish in the namespace can send NBIRTH, DBIRTH, or NDEATH for another node and replace its metric definitions, aliases, or online state. Check whether the host binds each group_id and edge_node_id to the authenticated MQTT client identity, and whether a new NBIRTH from a different client replaces a live node's birth without an intervening death. The NDEATH is the node's Will, its bdSeq increments on every connect, and the matching NBIRTH carries the same bdSeq, so verify the host compares an NDEATH's bdSeq with the current session's NBIRTH before acting on it. Report here a security outcome, such as forged birth metrics or aliases that make a later command reach a different metric; a spoof that only marks values stale belongs in `PROCESS-DATA-INTEGRITY.md`.

**Primary host STATE spoofing**
A client other than the primary host application can publish the retained STATE message on `spBv1.0/STATE/<sparkplug_host_id>`, so edge nodes see the host as online when it is not, or offline when it is, and publish or withhold births and data accordingly. Edge nodes configured with a primary host subscribe to that topic and must accept only a STATE timestamp equal to or later than the previous one. Check who may publish there in repository broker ACLs, whether edge-node code enforces the timestamp rule and parses the `online` and `timestamp` fields strictly, and whether one forged STATE with a far-future timestamp would make the node reject every later legitimate one. Verify that host ids are unique across the deployment's configuration. A STATE topic writable only by the host's own credential is the control; its absence from the repository makes the candidate `needs_validation`.

**Retained-message and wildcard subscription trust**
The application treats a retained message delivered at subscribe time as current, authoritative configuration, command, state, or identity, although any earlier publisher with access to the topic could have left it. The same defect arises when a client subscribes with `+` or `#` and dispatches whatever arrives into privileged handlers by topic text. Check which handlers act on retained deliveries, whether the code reads the RETAIN flag and sets Retain Handling and Retain As Published deliberately, who can clear a retained message with a zero-byte publish, and whether a topic parser trusts each segment it routes on. Defer generic wildcard and topic ACL scope to `PROTOCOLS-RPC-AND-MESSAGING.md` "Topic, routing-key, and subscription scope gaps"; report here only an industrial handler that grants authority from a retained or wildcard-matched message.

**Broker authorization denial read as success or silence**
The client ignores the reason codes that report a broker authorization denial, so a denied subscription to a command, STATE, or death topic looks like a quiet topic and a denied command publish is recorded as sent. In MQTT 5, SUBACK returns a reason per requested filter, such as 0x87 Not authorized or 0x80 Unspecified error, and 0x87 is also valid in PUBACK and DISCONNECT. Check that the code reads each SUBACK result and, for QoS 1 publishes, the PUBACK reason, and that any audit, approval, or command-history record is written from the acknowledgment rather than from the publish call returning. Confirm a security outcome: a command logged as delivered that was refused, an approval marked complete, or a monitor that cannot see node deaths or host STATE changes. A denied data subscription whose only effect is missing or stale values goes to `PROCESS-DATA-INTEGRITY.md`.

## Historian, device administration, and hostile peer attack classes (subagent_type: `general`)

**Historian write, replace, and backfill exposure through a read surface**
A query, export, connector, or agent tool meant only to read history also reaches insert, replace, delete, annotation, or backfill modes of the historian interface, or opens the historian connection with an identity that can write. Read the connector's mode and operation parameters, update-type enums, and default arguments. Check whether a caller-supplied option, bulk-import or backfill job, or "fill gaps" feature can overwrite or delete stored values for tags the caller cannot edit, and whether each change records the requesting user rather than the service account. Compare the credential the read path uses with the minimum the read needs; a broad credential alone is `needs_validation` until source shows a reachable write or delete from lower-trust input.

**Device and gateway administration surface exposure**
The software embeds, proxies, or drives the administration interface of a gateway, edge device, or protocol server, such as its web console, driver and tag configuration API, security and user settings, or restart commands, and a lower-trust user or network peer can reach it through the software. Find the code that calls or proxies those interfaces, the device credential it uses, and whether one stored administrator credential serves every application user. Check whether a configuration push takes tag addresses, scripts, endpoints, or credentials from user input, and whether an embedded console is proxied without the application's own authorization in front of it. Defer controller and device downloads to `OT-BOUNDARY-AND-CONTROL-WRITES.md` "Recipe, program, and configuration download exposure", shipped default credentials to `GOVERNANCE-CONFIGURATION-AND-CHANGE.md` "Default and fleet-shared credentials", firmware integrity to `SUPPLY-CHAIN-AND-RELEASE.md`, and generic management-plane reachability to `CLOUD-AND-DEPLOYMENT.md`. An administration path open only to application administrators, each acting under an audited identity of their own, is intended authority.

**Hostile server and device response trust**
A malicious or compromised OPC UA server, broker peer, historian, or field device returns content the client treats as trusted, and it reaches a path, query, template, command line, model prompt, or HTML sink, or drives dynamic type loading and deserialization. Candidate fields include display names, descriptions, engineering-unit text, browse names, node references, endpoint and referral URLs, data type definitions, Sparkplug metric names and properties, and transferred files. Trace each server-supplied string and structure from the decoder to its first security-relevant use, including browse references the client follows into another namespace or server and URLs that make it connect to hosts the configuration does not name. Defer decoder memory safety to `MEMORY-SAFETY-AND-BINARY.md`, unbounded arrays and recursion to `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md`, model-context sinks to `AI-AND-LLM.md`, and a response that only produces a wrong value to `PROCESS-DATA-INTEGRITY.md`.

**Caller-chosen plant connection targets**
A user, import file, tenant setting, message, or agent tool argument chooses the host, port, endpoint URL, or connection string the server then connects to, so a lower-trust caller uses the server's plant-network position to reach historians, gateways, brokers, controllers, or engineering hosts it cannot reach itself. Find every feature that adds a data source, tests or browses a connection, runs endpoint discovery, scans an address or unit-identifier range, or fetches a URL, and check who may set the target, whether a server-side allowlist of configured targets applies after name resolution and redirects, and whether a saved credential, certificate, or token is sent to a newly chosen host. Check whether error text, timing, or banners returned to the caller distinguish open, closed, and filtered ports or name the peer's product and version. Defer what a chosen hostile server returns to **Hostile server and device response trust**. A target change restricted to an administrator acting under an audited identity of their own is intended authority.

## Universal moves (apply across the above)

- Inventory every protocol endpoint the repository builds as client, server, publisher, subscriber, or gateway: library, configuration file, defaults, environment overrides, and test fixtures. For each, record security mode and policy, certificate validation callback, user token or broker credential, client id, publish topics, subscriptions, and writable nodes, registers, or command metrics.
- Start at every write, method call, command publish, history change, and device configuration call, and trace backward to the user input, scheduled job, agent tool, or bridged message that triggers it and the authorization checked on the way.
- Compare production, example, test, and development configuration for the same connection. Insecure flags, auto-accept options, None endpoints, and shared credentials often live in samples that installers and deployment scripts copy.
- Exercise hostile peers only through simulators, recorded fixtures, and in-memory brokers the repository ships, on isolated loopback, and stop at the formed request, the accepted forged message, the reached sink, or the connection a loopback stub receives in place of a caller-chosen host.

## Validation rules (apply before reporting ANY finding here)

1. Name the lower-trust principal or network position, the accepted input or forged message, the protocol identity under which it reaches the server, broker, or device, the control that should have stopped it, and the resulting write, command, method call, configuration change, credential, impersonated identity, or connection opened to a host the configuration does not name.
2. For OPC UA security mode, certificate, and user token claims, show that the setting is effective in a shipped or default configuration reachable from a non-test entry point. When the opposite endpoint, trust-list contents, or server configuration lies outside the repository, return `needs_validation`.
3. For MQTT and Sparkplug spoofing or command claims, cite the consuming or publishing code that acts without binding the message to the publisher's authenticated identity, plus any repository broker ACLs. Broker ACLs or bridge configuration absent from the repository make the candidate `needs_validation`.
4. For write and command reachability, stop at the formed request frame, protocol call, or command message in a unit test or repository simulator. Send nothing to a real device, server, or broker, never describe a physical consequence as observed, and return any lead touching a safety instrumented system or interlock as `needs_validation` with the safety system's owner named.
5. For hostile-response claims, show the server-controlled field reaching a security sink or capability. A result that is only a wrong value, timestamp, quality, or identity is a `data_integrity` record under `PROCESS-DATA-INTEGRITY.md`, and a decoder crash belongs to `MEMORY-SAFETY-AND-BINARY.md`.
6. Return `confirmed` only with the complete path from lower-trust input or peer to the protocol operation, the missing or bypassed control, and an observed formed request, accepted forged message, or reached sink. Return `needs_validation` with the exact endpoint, trust list, broker ACL, bridge, gateway, device, or network-reachability fact required and a safe owner-observed check that resolves it.
