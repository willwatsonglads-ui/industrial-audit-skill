# Model, Batch Analytics, and Simulation Hunting

#### When to use this file

Reach for this file when the target computes a result that no instrument measured and delivers it to a person, a record, or an automated action: soft sensors and inferential estimates, forecasts and anomaly scores, batch and golden-profile comparisons, yields, mass balances, OEE and other KPIs, process simulations fed with plant data, data reconciliation, parameter fitting, and optimizers. The data path is measurements and lab results → selection, alignment, and the training or reference set → model, reference profile, or simulation → estimate, verdict, KPI, or recommendation → consumer. The classes here produce `data_integrity` findings. Use `PROCESS-DATA-INTEGRITY.md` for how the inputs were acquired, stored, and aggregated, `PIPELINES-JOBS-AND-RELIABILITY.md` for the jobs that run these calculations, `ALARMS-HMI-AND-DISPLAY.md#Modeled values styled as measurements` for how a computed result is styled on screen, `AI-IN-PLANT-OPERATIONS.md` for language models and agents and for any path from a recommendation to an action, and `PROCESS-DATA-INTEGRITY.md#Calculated value formula and input-version drift` for the version stamp on a stored result.

Split large targets by computed output, then by path: fit or build time, run time, and re-run or backfill.

## Core discipline (include in every agent prompt for this domain)

```
- A computed result is a claim about the plant. It holds only when every input was valid and current and lay inside what the model, reference, or simulation was built for, and when the calculation itself finished. The defect is a result delivered as valid when one of those failed.
- Every result has three honest states: valid, invalid, and unknown. Hunt for the path where unknown (no data yet, a gap, a failed solve, an input out of range) comes out as a normal-looking number, a pass, or 100 percent.
- Compare fit time with run time. Selection, alignment, fill, scaling, units, and retrieval mode used to build a model or reference must equal those used when it runs.
- No attacker is required. Name the ordinary condition: an input goes bad or freezes, a batch starts, holds, or runs long, a lab result arrives late or censored, a grade changes, a solver fails, the unit starts up or shuts down.
- Work from source and in-repo fixtures. Stand in for a trained model, simulator, or solver with a small stub when the real one cannot run in the sandbox, and stop at the stored estimate, verdict, KPI, or published result, never at a physical consequence.
- Use `confirmed` for a source-complete path plus a bounded fixture run that shows the wrong delivered result. Use `needs_validation` for facts outside the repository: model accuracy on real plant data, true process dead time, whether a fitted range or property method suits the site, and the behaviour of a simulator that cannot run locally.
```

## Estimate validity attack classes (subagent_type: `general`)

**Estimate quality not derived from input state**
A soft-sensor estimate, forecast, score, or other computed tag is published as good, or with no quality at all, because the calculation ran, while an input was Bad, Uncertain, stale, frozen, substituted, or filled. Find where the result's quality is set and trace it back: it should be the worst input quality, lowered again when any input is older than its own age limit, has not changed for longer than the signal plausibly holds, or was imputed in the feature step. Check forward-fill, mean imputation, and `get(tag, 0)` on the run-time path for a flag that reaches the output and a limit on consecutive filled samples. Feed one Bad, one stale, and one missing input and read the stored result. An estimate from degraded inputs is not a defect when its quality or a reason field says so on every surface it reaches.

**Extrapolation beyond the fitted range**
A model, correlation, or reference is evaluated outside the region its fitting data covered, such as start-up, a new grade, fouled equipment, or a sensor at its limit, and returns a confident number: a linear model extrapolates, a tree model holds its edge value, and neither signals. Check what the saved model knows about its own domain: per-input ranges, the mode, grade, or equipment it was fitted for, or a distance statistic such as leverage, Hotelling's T-squared, or a reconstruction residual. Check that the run-time path compares each input vector with it and downgrades or withholds the result, and that every fit-time filter (steady state only, one grade, one unit) has a matching run-time gate. A result is a finding only when the stored model can show the input lay outside what it was fitted on; whether that range is adequate for the site is `needs_validation`.

**Clamped, held, and defaulted results**
A result outside a plausible range is clipped to the limit, or a failed calculation republishes the previous result with a new timestamp, returns zero, or returns a configured default, so a failure reads as a steady value or a reading at the limit. Read `clip`, `min(max(...))`, `nan_to_num`, and every exception handler around the calculation and its publish step, and check which value, timestamp, and quality leave on each branch. Check that non-finite results stop at the writer instead of becoming zero, null, or the last good value. A clamp that sets a flag and keeps the raw value, or a hold that keeps its original time with a degraded quality, is not a defect.

**Online correction from unvetted results**
A bias update, recalibration, automatic refit, or parameter update takes each new lab result or measurement as truth, so one preliminary, retracted, censored, mis-keyed, or misaligned result shifts every later estimate, or the updated model replaces the previous one with no record. Check that the update reads the result's status and sample time, bounds the step it may take, rejects a result outside a plausible residual, and records old and new values with a version that each later estimate carries. Check what a restart does to the correction state. Use `AI-IN-PLANT-OPERATIONS.md#Model, prompt, and tool change outside change control` when the update bypasses change control the software applies elsewhere. A correction that is gated, bounded, and recorded is not a defect.

## Training and evaluation data attack classes (subagent_type: `general`)

**Feature and target time misalignment**
Training pairs join a lab result to process data at its result, approval, or entry time instead of its sample time, ignore the delay between the process measurement and the sampled material, or build features with an as-of join that has no tolerance, a centred window, a back-fill, or an interpolation spanning the sample time, so the model learns from the wrong moment or from the future. Check each join key and direction, the tolerance on every as-of join, `center=True`, negative shifts, back-fill, and resample labels: every feature window must end at or before the instant the estimate would be made online. Compare the fit-time feature code with the run-time feature code line by line. The finding is a training row built from a value that is unavailable, or different, at the matching run-time moment; the correct delay for the process is `needs_validation`.

**Training-set selection bias**
Rows are removed or altered before fitting, so the model cannot be right in a region it still answers for: censored results dropped or replaced by the limit or a fraction of it, unparseable values coerced to missing and dropped, outlier rules that delete real excursions, rows with any gap discarded, retests and duplicates counted as independent samples, and compressed or interpolated history read as raw samples. Read every coercion, `dropna`, quantile or z-score filter, and deduplication key, count what each removes and where in the range it falls, and compare the retrieval mode of the training query with the live feed. The finding is an estimate delivered as valid in a range whose data the pipeline removed or altered, with nothing recorded; an exclusion stored with the model and enforced as a run-time limit is not a defect.

**Accuracy figures from leaky evaluation**
An accuracy, error, or confidence figure that the software shows, stores with a model, or uses to gate promotion is computed on the fitting rows, on a shuffled split of autocorrelated or batch-grouped data, after scaling, imputation, or feature selection fitted on all rows, or as one pooled number that hides bias at a range end or at a specification limit. Check that splits are time-ordered or grouped by batch or campaign with a gap covering the feature lags, that every fitted step sits inside the cross-validation pipeline, and that error is reported by range. This class applies only where the figure reaches a person, a record, or a promotion gate; a metric in a notebook that nobody is shown is not a finding.

## Batch and event comparison attack classes (subagent_type: `general`)

**Batch boundary and identity errors**
A batch, run, or campaign's start and end are derived from a threshold crossing, a clock window, or one tag's edge, so a restart, hold, aborted batch, or back-to-back pair merges or splits wrongly, samples near the boundary join the wrong batch, or a reused batch identifier pulls in an earlier batch's data. Trace how each boundary is derived and whether the batch system's own events are used where the target has them; check an open batch with no end yet, a restart, a boundary inside the repeated daylight-saving hour, and an identifier that recurs. A derived boundary is not a defect unless data from outside a batch enters its profile, total, or record, or data inside it is left out, with no marker.

**Profile alignment across unequal batches**
Batches that differ in length, contain holds, or run at different rates are compared at equal elapsed time or after stretching to a common length, so a normal batch reads as deviating, or time warping absorbs a real delay and reports alignment. Check the reference profile's axis (elapsed time, time within phase, or a progress variable), whether holds are events, whether the tolerance band is computed after alignment and per phase, whether warping is constrained and its amount reported, and whether the live comparison uses only data up to now instead of the final batch length. An alignment choice is not a defect unless it changes a verdict or deviation that is delivered without showing the alignment used.

**Verdict without sufficient data**
A comparison, limit check, conformance test, or anomaly detector returns "within limits", "matching", "normal", or 100 percent when it had no data, too little data, or missing points: an empty series passes `all()`, a missing value fails every out-of-limit test, a gap is bridged by resampling or interpolation before the comparison, and a batch that has just started is declared on profile. For each verdict, find its third state, the minimum count per window or phase, and whether filled points count as evidence, then run it on an empty input, an all-missing input, and an input with a gap longer than its normal sample interval. This class applies to every verdict in the target, not only to batch comparison. A distinct, visible "no data" or "insufficient data" state is not a defect.

**Reference set and envelope construction errors**
A golden profile, envelope, baseline, or learned threshold is built from the wrong or too few references: another recipe, grade, unit, or equipment, abnormal batches, or periods that contain outages, and a band of mean plus or minus a multiple of the standard deviation collapses where the references agree and is undefined where few of them reach. Check the metadata stored with the reference and enforced at compare time, the minimum reference count per point, a floor on band width, the rule that excludes abnormal batches, and whether an edit replaces the reference in place. The finding is a comparison that runs against a reference its own metadata shows does not apply, or against a band that is degenerate at points still compared; how representative the chosen batches are is `needs_validation`.

## Period, KPI, and balance arithmetic attack classes (subagent_type: `general`)

**Production-day and shift boundary errors**
Period totals, shift reports, and daily KPIs cut at calendar midnight in the server's zone or in UTC where the plant's production day or shift starts at another hour, treat every day as 24 hours across a daylight-saving change, count an event that spans a boundary wholly in one period or in both, or present a period that is still open as complete. Check where the period calendar comes from, that events are clipped to the period before they are summed, that rates divide by the period's actual length, and that an open period carries a marker. A calendar-day report labelled as such is not a defect.

**Ratio, rate, and rollup arithmetic errors**
A KPI is rolled up as an average of ratios or an average of averages over unequal bases, a zero denominator is shown as 0 or 100 percent, totals add values in mixed units, the components of one KPI come from different windows or process stages, a figure above 100 percent is clipped without a flag, or overlapping downtime events are counted twice. Read each KPI's formula against the definition the software states, recompute one mixed fixture by hand as a ratio of sums, and include a period with no production. A stated definition that differs from another common one is not a defect; a rollup that disagrees with the software's own definition is.

**Balance closure by assignment**
A mass, energy, or inventory balance is closed by assigning the residual to one stream, loss term, or adjustment, by consuming components at their planned quantity instead of the measured one, or by overwriting measurements with reconciled values, so the balance always closes and a failed meter or missing consumption cannot show. Find every term computed as a total minus a sum, every planned or backflushed quantity standing in for a measurement, and every reconciled value written over its raw measurement, and check that the output keeps raw and adjusted values apart with the size of each adjustment. A calculated term labelled as calculated, with the residual reported, is not a defect.

## Simulation and digital twin attack classes (subagent_type: `general`)

**Solver status ignored and failed-solve reuse**
A flowsheet, optimizer, equation solver, or fit returns without converging, and the code reads its variables anyway, or a failed, skipped, or timed-out run leaves the previous solution in the model objects and the publish step stamps it with the new time. After every solve, fit, and property call, find the check of the solver's own status: a success flag, a termination condition, per-object error state, and convergence of each recycle loop. Read each exception handler for a returned default or cached result. Check that the published time is the time of the input data, that a failed run writes a failed status instead of values, and that a run in which only some cases solved publishes only those. A result is not a defect when it is published only after the status check passes and carries the status with it.

**Measurement-to-model basis mismatch**
A plant value is set as a model input in a different unit or basis from the one the model expects: gauge for absolute pressure, Celsius for kelvin, mass for molar or standard-volume flow, one reference temperature and pressure for another under the same "standard" or "normal" label, wet for dry, mass for mole fraction, percent for fraction. Trace each tag-to-variable mapping to a per-tag table that states unit and basis, and treat hand-written offsets and factors on tag values as leads. Check that a composition is tested for its sum before it is set, since a library that renormalizes hides a wrong basis, and that the same mapping applies when model output is compared with a measurement. The finding needs the mapping and the model's expected basis both visible in the repository; the true unit of a plant tag is `needs_validation`.

**Unsteady and non-simultaneous inputs to a steady-state model**
A steady-state model is solved from a snapshot taken during a start-up, grade change, or upset, or from inputs read at different instants, held from an earlier good value, or frozen, and the gap between model and plant is then reported as equipment condition. Check that the run path tests several key tags for steadiness and stores the result, that averaging windows are stated, and that each input carries its timestamp and quality, with a limit on age and on the spread of timestamps across inputs. A model that runs on a fixed schedule with none of these checks is a candidate once its output is delivered as a measure of the plant; the right steadiness test and window are `needs_validation`.

**Property and correlation validity range overrun**
A property method, equation of state, or correlation is evaluated outside the temperature, pressure, or composition range it is valid for, with a phase imposed that the state does not have, with interaction parameters that were silently defaulted, or with enthalpies from two sources that use different reference states, and returns a number. Check each property call for a range test before it and for a caught error turned into a default after it; check that missing parameters are detected instead of defaulted, and that the property method and its version are stored with every result. A range check that withholds or marks the result is not a defect; whether a method suits the site's fluids is `needs_validation`.

**Parameter fitting that absorbs bad data**
An automatic fit or self-tuning step adjusts model parameters to match measurements that were bad, biased, transient, or from a single operating point, so a sensor fault becomes a changed equipment parameter, and the new set overwrites the validated one. Check that the fit reads the solver's success state and which bounds are active, refuses a parameter resting on a bound, and tests a candidate against held-back data before it replaces the current set. Check that parameter sets are kept append-only with the data window and fit statistics, and that every result names the set that produced it. A fit that is gated, recorded, and reversible is not a defect.

**Optimization result outside the validated envelope**
An optimizer or what-if calculation recommends operating values beyond the range the model was validated for, beyond limits the model does not contain, or from a solve that stopped at an iteration limit or a local solution, and presents them as optimal. Check that each recommendation carries the solver's termination state, the constraints that were active, and whether any input or recommended value lies outside the stored validation range, and that an infeasible or unfinished solve yields no recommendation. Any path from a recommendation to a write belongs to `AI-IN-PLANT-OPERATIONS.md#AI recommendation-to-action bypass` and `OT-BOUNDARY-AND-CONTROL-WRITES.md`. A recommendation labelled with its limits and solver state is not a defect.

## Universal moves (apply across the above)

- Build a condition table for each computed output. Rows are the ordinary conditions: an input Bad, stale, frozen, missing, or out of range; no data yet; a gap; too few points; a censored or retracted lab result; a failed or unconverged calculation; a restart. For each row, record what the output delivers. Any row where the honest answer is "unknown" and the output is a normal-looking number or a pass is a candidate.
- Replace the model, simulator, or solver with a stub that fails, returns non-finite values, or reports no convergence, and read what the publish step writes. This needs no trained model and no simulator licence.
- Diff fit-time code against run-time code: filters, joins, fills, scaling, units, and retrieval mode. Every difference is a lead, and so is every fit-time filter with no run-time gate.
- Run each verdict and KPI on an empty input, an all-missing input, a single point, and a period with a zero denominator.
- Grep for the idioms that cause these defects: `quality = "good"` literals, `except` blocks that return a value, `clip` and `nan_to_num`, `dropna` and coerced numeric parsing, as-of joins without a tolerance, shuffled splits, `all(` over a filtered list, solves with no status check, and literal offsets such as 273.15 or 101325 applied to tag values.

## Validation rules (apply before reporting ANY finding here)

1. Name the inputs with their value, time, unit, quality, and identity; the model, reference, or simulation with its version; the computed result; the consumer; the decision it informs; and the ordinary condition that triggers the difference.
2. Show what the result should have been: a different value, a lower quality, or "unknown". Show that the delivered result differs and that nothing at the destination reveals it. Check every quality, reason, status, and version field the consumer could read.
3. Reproduce with a fixture through the in-repo code in the sandbox, using a stub for any model or solver that cannot run there, and stop at the smallest wrong stored estimate, verdict, KPI, or published value. A stub shows what the code does with a failed or out-of-range calculation; it does not show that the real model fails.
4. Keep the candidate `needs_validation` when the outcome depends on facts outside the repository: the model's accuracy, the process delay, the adequacy of a fitted range or reference set, the validity of a property method for the site, or the unit a plant tag is really in. A lead that touches a safety instrumented system or interlock is `needs_validation` with the safety system's owner named.
5. Rule out designed behaviour the consumer can see: a result marked as estimated with its quality, a labelled provisional figure, a stated KPI definition, a clamp that sets a flag.
6. Return `confirmed` only with the complete path and an observed wrong delivered result from a source-complete trace and bounded local execution. Return `needs_validation` with the exact model, process, or site fact required and the fixture or owner check that would settle it.
