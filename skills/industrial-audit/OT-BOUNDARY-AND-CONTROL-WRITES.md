# OT Boundary and Control-Write Hunting

#### When to use this file

Reach for this file when the target can send anything toward a controller, SCADA or DCS server, batch engine, or field device, whether a value write, method call, command message, recipe, program, configuration download, or mode change, or when it sits on a network path between business and control systems: a DMZ relay, edge gateway, replication or store-and-forward service, remote-access path, or integration that a control-side system polls. Reach for it as well when plant software opens listeners, dials plant hosts, or states where it runs and what leaves the site (a network level or zone, on-premises, outbound-only, no telemetry): the containment classes in the zone group apply even when no write path exists. The important data flow is *lower-trust principal or ordinary plant condition → write-capable primitive or zone crossing → request emitted toward the control side, or a listener, connection, or data flow that crosses the zone boundary the software claims*. Every class here produces `security` findings; a write that carries a silently wrong value through an ordinary conversion with no lower-trust actor belongs in `PROCESS-DATA-INTEGRITY.md` as `data_integrity`. Use `PROTOCOLS-RPC-AND-MESSAGING.md` for generic broker, replay, and delivery semantics, `INDUSTRIAL-PROTOCOLS-AND-DEVICES.md` for OPC UA, MQTT, Sparkplug, and fieldbus protocol security, `AI-AND-LLM.md` and `AI-IN-PLANT-OPERATIONS.md` for agent tool use that reaches a write path, `GOVERNANCE-CONFIGURATION-AND-CHANGE.md` for role, change-control, out-of-band configuration, and remote-support lifecycle, and `RECORDS-AUDIT-AND-SIGNATURES.md` for what a signature record means.

Split large systems by write-capable primitive, zone crossing, and operating mode.

## Core discipline (include in every agent prompt for this domain)

```
- A "read-only" label, a disabled flag, a missing write button, or a comment is not evidence. Enumerate every write, call, command, publish, and download primitive the build links, and every configuration that can reach it.
- Name the write at its last software hop: the exact endpoint, node, register, or topic, the value, unit, and data type, and the principal whose authority the request carries.
- Approval, writable-point allowlist, write-enable switch, and permission check are separate controls. Check each one after arguments are final and immediately before the request leaves, on every direct, queued, retried, batched, and replayed path.
- Zone claims come from code and configuration: which side listens, which side dials, and what instructions flow back over each established connection. Firewall, unidirectional gateway, and routing behavior outside the repository is not observed.
- Never connect to a plant system or send a write, command, download, mode change, or rebirth request, and never resolve a plant host name found in source. Prove the path from source and in-repo recording stubs, stop at the emitted request, and never treat a physical consequence as the result.
- Use `confirmed` only when source and bounded local evidence show a lower-authority principal or ordinary condition causing a control-directed request that an intended control should have stopped, or, for the containment classes, a shipped listener, outbound request, or opened connection that contradicts the software's own placement or egress claim or reaches a sensitive operation without authentication. A firewall that might block the path is a condition to record, not a blocker, when the defect is the software's own shipped behavior. Use `needs_validation` when the result depends on which networks can actually reach which (an external firewall rule, routing, broker ACL, gateway mapping, device-side access level, or remote-access appliance setting), and for every lead touching a safety instrumented system, with the safety system's owner named.
```

## Write-path discovery attack classes (subagent_type: `general`)

**Read-only claim and latent write-path gaps**
Software described as read-only still links a client that can write, call methods, publish commands, or download, and a reachable path exercises it: a disabled-by-default feature, a feature flag, a test-only helper compiled into the release, a generic "set value" wrapper, or a library default that writes a cached or initial value back on connect or reconnect. Grep every protocol client, driver, and SDK in the build for write, call, command, publish, download, and combined read/write primitives (for example a Modbus Read/Write Multiple registers request, which writes while it reads), then trace each call site back to an entry point and the flag or configuration that guards it. Check build profiles, plugin loaders, scripting hooks, and admin consoles that can reach those call sites in a production build. An unused write primitive in a linked library is not a defect unless a source path in a shipped configuration reaches it.

**Indirect write-down through an intermediate system**
The target never speaks a control protocol itself but writes to a system that does: a broker command topic, a shared database table or file drop that a gateway, SCADA script, or batch engine polls, a historian or MES field that a bidirectional tag mapping pushes down, or a business order that a downstream system turns into a download. Trace each outbound write the target makes to another system, then read the in-repo mapping, schema, integration contract, or deployment configuration of that system to establish whether the destination feeds a control-side consumer. Compare the gates on this indirect path with those on any direct write path; a read-only label on the direct client does not cover them. A write into a business system is not a control write unless a source-visible or named downstream consumer carries it toward a controller, and when that mapping lives outside the repository the candidate is `needs_validation` naming the mapping, topic, or table whose direction decides it.

**Recipe, program, and configuration download exposure**
A path that sends a recipe, parameter set, phase or procedure definition, controller program or logic, device configuration, or firmware image toward a controller or batch engine is gated more weakly than a single-value write, or not at all. Find every download, deploy, push, sync, import, and "apply configuration" operation, and compare its authorization, approval, allowlist, and audit with the single-point write path. Verify that the downloaded artifact is the reviewed artifact (content hash or version bound into the approval), that a bulk download authorizes every target it contains, and that import, restore, or site-sync jobs cannot trigger a download as a side effect. A download that requires the same authority and approval as the equivalent individual writes is not a defect.

**Mode-change and command-method exposure**
Operations that change operating state rather than a value (start, stop, hold, abort, reset, auto/manual/cascade transfer, run/program switch, force, loop or device enable) are exposed through method calls, command topics such as Sparkplug NCMD, or command records that bypass the gates applied to value writes. Enumerate method-call, command-message, and state-transition paths alongside value writes, and check whether the allowlist, approval, and permission model classify them as writes at all. Verify that a command encoded as an ordinary value write, such as a mode word, command bit, or Boolean trigger, receives the same treatment as the explicit command. Displaying the current mode read-only is not a finding.

## Write authorization and binding attack classes (subagent_type: `general`)

**Control-write approval binding to tag, value, unit, and target**
An approval, signature, or confirmation covers a description of the write rather than the normalized object the executor sends, so the executed request can differ in tag, node or register address, value, engineering unit, scaling, data type, target server, or site. Compare the object that is hashed, signed, or stored at approval with the object built at execution, field by field, and look for resolution steps that run after approval: alias or browse-path lookup, namespace or index resolution, unit conversion, scaling, rounding, type coercion, and endpoint selection by site or environment. Check that a batch approval authorizes exactly its members and that adding, reordering, or substituting a member invalidates it. This class asks only whether the signed object is the executed object; the record meaning of the signature belongs to `RECORDS-AUDIT-AND-SIGNATURES.md`.

**Approved-write staleness, expiry, and replay**
An approved or queued write executes long after approval, more than once, or under conditions the approval did not cover: no expiry, an expiry checked at enqueue rather than at send, no single-use nonce, a retry or resumed job that resends a completed write, or an accepted replay of a signed request. Trace the approval record from creation to execution and through restart, failover, queue redelivery, scheduler catch-up, and backup restore. Where the code itself records a precondition at approval time (an operating mode, a current value band, a permissive flag, a revision of the writable list, the approver's role), verify that it is re-read at execution and that a changed precondition blocks the send. Do not invent preconditions the software never claims to check; the defect is a gate the source defines but evaluates only once.

**Writable-point allowlist matching and ownership gaps**
The list of points the software may write admits more than its owner intended, or can be changed by the same principal it constrains. Read the matching code for prefix, wildcard, or regular-expression matches, case folding, alias or browse-path comparison where a node identifier was intended, namespace index reuse after a server restart, register offset arithmetic, and the default when the list is empty, missing, or fails to parse. Check whether the role that writes points can also edit the list through the product's own API or screens, and whether a removed entry stops matching at once or survives in a cache, a running session, or a queued write. Out-of-band edits and restores that bring back withdrawn entries belong to `GOVERNANCE-CONFIGURATION-AND-CHANGE.md`; a device- or server-side access level that would refuse the write is `needs_validation` evidence unless the repository ships that server's configuration.

**Write-enable switch default and disable propagation**
The switch that turns control writes on is default-on in some build, profile, environment, tenant, or site, can be set through a request field, a per-user preference, or a setting a lower-privileged role controls, or leaves queued, scheduled, and in-flight writes running after it is turned off. Find every read of the switch and check whether it is evaluated per write at send time or once at startup, whether per-site and global switches combine by the stricter value, and whether disabling it cancels or blocks pending work. Compare the documented default with the effective value in every shipped configuration, container image, installer, seed script, and test fixture that a release build loads.

## Zone and conduit crossing attack classes (subagent_type: `general`)

**Outbound-only claim and inbound command channel gaps**
A component described as outbound-only, or placed in a control zone, accepts inbound connections or receives instructions it executes there: a listening port, a management or debug endpoint, a callback URL, a reverse tunnel, or a persistent outbound connection (WebSocket, long poll, broker subscription) over which the business side sends work. Read the listener, bind-address, and dial code, then list every message type that flows back down each established connection and the handler each one reaches. An outbound connection that carries back only acknowledgements, flow control, or read requests answered read-only is not a defect; one that carries write, command, download, configuration, or remote-shell requests is. Firewall and routing behavior outside the repository is `needs_validation`.

**DMZ brokering and pass-through relay gaps**
A component meant to terminate business-side requests in a DMZ and re-originate a narrow set toward the control zone instead forwards them: a generic TCP, HTTP, or protocol proxy, a caller-selected target host, port, endpoint, or node, a pass-through of raw protocol frames, or a service credential valid in both zones. Trace what the business-side caller controls in each relayed request and compare it with the fixed set of targets and operations the relay is meant to permit. Check that the relay authenticates the business-side caller rather than trusting network position, and that responses cannot carry control-zone credentials, session tokens, or connection strings back out. Generic request-forgery mechanics belong to `ATTACK-CLASSES.md`; this class covers zone-crossing scope.

**Store-and-forward and replication direction reversal**
A path built to move data one way, from the control side to the business side, can carry data the other way or replay it: two-way replication or sync where one-way was intended, conflict resolution that writes the business-side copy back to the source, a backfill or correction job that writes to the source system, or a store-and-forward buffer of commands released after an outage. Read the replication, sync, broker bridge, and buffer configuration for direction, topic or table patterns, conflict policy, and authoritative side, including a bridge whose topics run both ways or match the whole tree, and trace what happens to buffered writes on reconnect: expiry, deduplication, ordering, and re-authorization under the current switch and allowlist. Compare restore and resynchronization paths with the normal path. One-way movement whose reverse direction requires a separately authorized operation is not a defect.

**Shipped listener and network-default exposure**
A release configuration opens a listener on more interfaces than the software needs or claims, or starts one by default that a site never asked for: a bind to all interfaces, a remote-debug, profiler, or management port, an embedded protocol server or broker, a container with host networking or a published port, a firewall rule the installer adds, or a discovery responder, multicast or broadcast announcement, or router port-mapping request. Build the listener table from every installer, service definition, container file, chart, and default configuration a release loads, recording bind address, port, protocol, authentication, and default state, and trace each listener to the handlers it reaches. Report a listener that contradicts the software's own placement or listener claim, or that reaches a write, command, configuration, credential, or code-execution handler without authentication from a non-loopback interface. The same listener reached through `CLOUD-AND-DEPLOYMENT.md#Unexpected service or management-plane reachability` is one root cause under one fingerprint; a documented listener bound to the interface it needs and authenticated on every sensitive handler is not a defect, a listener that only a test or development profile opens is not shipped, and whether a site firewall admits a given peer is `needs_validation`.

**Undeclared egress and proxy routing**
Plant software that claims on-premises operation, no telemetry, or a fixed set of destinations still sends data off the site or out of its zone, through telemetry, crash and error reporting, update and license checks, cloud sync, webhooks, SDK analytics that are on by default, or browser assets loaded from public hosts; or traffic meant to stay inside the plant leaves through a proxy taken from the environment, system settings, or auto-configuration. List every outbound client with its destination, trigger, payload, the setting that disables it, and its proxy handling, then check which still run, and with what payload, under the software's on-premises, offline, or no-telemetry mode. Count host names, addresses, endpoint URLs, tag lists, and connection strings in a payload as plant data, and check that clients for plant hosts bypass the proxy and keep certificate verification on when a proxy is set. Where the software claims an egress allowlist, verify that every client uses it and that it is checked after redirects and name resolution rather than on the host-name text. A destination the software documents with its payload, or a client that is off by default and enabled only by an administrator, is not a defect; site egress filtering outside the repository is `needs_validation`, and model and embedding providers belong to `AI-IN-PLANT-OPERATIONS.md#OT data pull and egress beyond the stated boundary`.

## Access path, artifact, and mode attack classes (subagent_type: `general`)

**Remote-access reach beyond the named control-zone asset**
A remote-support, vendor, or integrator session granted for one asset or task can reach other control-zone hosts, ports, devices, or operations: a tunnel or port forward whose destination the remote party chooses, a jump service that exposes a whole subnet, a screen-share or shell on a host that holds engineering or write credentials, or a session token accepted by services beyond the one named in the request. Trace the session object from request to the connection it opens and compare the destinations, protocols, and operations it permits with the asset and task recorded in the request. Check whether the target scope is enforced by the component that opens the connection or only displayed to the approver. Expiry, revocation, persistence, and the audit of support sessions belong to `GOVERNANCE-CONFIGURATION-AND-CHANGE.md`; scope enforced only by a remote-access gateway outside the repository is `needs_validation`.

**Engineering project and controller-artifact trust**
The software stores, converts, transfers, or stages engineering project files, controller program exports, logic, device configuration backups, or firmware images, and a lower-trust principal can supply, replace, or read them. Check upload and import paths for path traversal or archive extraction into staging folders that an engineering tool or download job reads, verify that a staged artifact is bound by hash or signature to the reviewed version, and check whether exports, backups, previews, or diffs disclose credentials, keys, or device passwords embedded in project files. Use only in-repo fixtures, and never open a project in an engineering tool or move one toward a device.

**Bypass, maintenance, and simulation mode leakage**
A mode that relaxes control-write gates (bypass, maintenance, commissioning, emergency, simulation, demo) can be entered by a principal without the authority the mode requires, persists past its window, applies to more assets than it names, or sends writes meant for a simulator to a live endpoint. Find every mode flag and the write gates it disables, then check who can set it, whether it is scoped to one asset or the whole site, and whether simulation and live endpoints are selected by a value that a user, import, or site setting can change. Verify that a simulation mode holding live connection details cannot fall back to them on error or reconnect. Test-mode flags shipped in production builds and break-glass account attribution belong to `GOVERNANCE-CONFIGURATION-AND-CHANGE.md`; a documented bypass with its stated authority, scope, and expiry is not a defect.

**Safety instrumented system adjacency**
A write path, allowlist entry, mode, artifact, or network path appears to reach a safety instrumented system, interlock, trip, permissive, or safety bypass: points named or grouped as safety, a safety-zone endpoint in configuration, or a bypass or override command. Record the source location, the reaching path, and the gate in front of it, then stop. Do not assess the safety function, its integrity, or the physical effect of the request, and do not reason about whether a bypass would be safe. Every such lead is `needs_validation`, with the safety system's owner named as the blocker.

## Universal moves (apply across the above)

- Build a write-primitive table first: every client method, function code, service call, command topic, method identifier, and download routine the build links, with its callers, the gates in front of it, and the target it resolves at send time.
- Draw the zone map from source: each process, the zone its configuration places it in, which side listens and which dials on each connection, what flows in each direction over it, every outbound destination, and each stored credential with every connection that uses it. A credential used on both sides of a claimed zone boundary is a lead for **DMZ brokering and pass-through relay gaps**; whether the two targets really sit in different zones is `needs_validation`.
- Compare direct, queued, batched, scheduled, retried, replayed, resumed, imported, restored, and multi-site paths for the same write. Every gate must hold on each one, evaluated after final arguments.
- Diff configuration across build profiles and modes: production, simulation, test, demo, maintenance, and emergency. Tests that assert a write is blocked show intent; look for the path they do not exercise.

## Validation rules (apply before reporting ANY finding here)

1. Name the lower-authority principal or ordinary trigger, the write-capable primitive or zone crossing, the control that should stop it, the exact target (endpoint, node, register, or topic, plus value and unit), and the request the software emits. For a containment class, name instead the listener, outbound client, or connection feature, the claim or control it contradicts, and the bind address, destination, or target host it produces.
2. Prove reachability from an entry point that principal or condition can reach in a shipped configuration. Dead code, test-only paths absent from release builds, and settings only a principal who already holds write authority can change are not findings unless that setting is itself the crossed boundary.
3. Observe the result at the last software hop: a request captured by an in-repo recording stub or mocked client, a queued command record, or the message the code would publish. Send nothing to a device or simulator beyond the single dummy message `SKILL.md` allows, and never cite a physical consequence.
4. For binding, staleness, and replay claims, compare the normalized approved object with the executed object field by field, and show the divergent, expired, or repeated execution in a bounded local test.
5. For zone, relay, remote-access, listener, and egress claims, cite the listener, dial, and forwarding code and the shipped configuration that makes it effective. Source can establish a bind address, a default-on state, a hard-coded or default destination and its payload, a proxy-routing decision, and a connection to a caller-chosen host; observe them in the sandbox with a loopback stub, a stub name resolver, or a capturing sink, never a real address. When the result depends on which networks reach which (a firewall rule, routing, unidirectional gateway, broker ACL, remote-access appliance setting, or device access level outside the repository), the candidate is `needs_validation`; when it does not, record those controls as conditions, not blockers.
6. Return `confirmed` only with a complete source trace from entry point to emitted control-directed request and the control it bypassed, or, for a containment class, from shipped configuration or lower-trust input to the observed listener, outbound request, or connection and the claim or control it contradicts. Return `needs_validation` with the exact missing mapping, network, broker, device, or remote-access fact and a safe owner-observed check, and for any lead touching a safety instrumented system, interlock, or safety bypass, name the safety system's owner as the blocker.
