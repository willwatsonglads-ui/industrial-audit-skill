# Process-Data Integrity Hunting

#### When to use this file

Reach for this file when the target moves plant values from where they were produced to where a person, record, report, model, or automated action uses them: historian and time-series ingest, OPC UA and MQTT readers that store or forward values, tag mapping and asset models, unit conversion and scaling, aggregation and interpolation, ingest checkpoints and store-and-forward buffers, backfill and replay, data exports, and lab, batch, or manual data imports. The data path is source sample → reader or gateway → mapping and conversion → store → query, aggregate, or export → consumer. The classes here produce `data_integrity` findings; a path where a lower-trust principal deliberately injects or alters values belongs in the security files. Use `INDUSTRIAL-PROTOCOLS-AND-DEVICES.md` for protocol session, birth, and device behavior, `PROTOCOLS-RPC-AND-MESSAGING.md` for message ordering and duplicate delivery as security concerns, `ALARMS-HMI-AND-DISPLAY.md` for how values, gaps, and quality are rendered on screens, `RECORDS-AUDIT-AND-SIGNATURES.md` for audit trails and signed records, `PIPELINES-JOBS-AND-RELIABILITY.md` for the jobs that move and derive these values, `MODELS-BATCH-AND-SIMULATION.md` for estimates, verdicts, and KPIs computed from them, and `AI-IN-PLANT-OPERATIONS.md` for what language models do with the inputs this file checks.

Split large targets by source family, write path (live, buffered, backfill, manual), and consumer (API, export, report, model input).

## Core discipline (include in every agent prompt for this domain)

```
- Track five attributes for every sample: value, timestamp, unit, quality, and identity. The defect is a hop that changes or drops one without making the change visible to the consumer.
- No attacker is required. Name the ordinary plant condition that triggers the difference: communication fault, restart, reconnect, clock or daylight-saving change, late or corrected data, rename, unit change, counter reset, or concurrent writer.
- Absence is information. Keep "no change", "no data", and "bad data" distinct at every layer; compression and report-by-exception make silence normal, so treat neither silence as an outage nor a frozen source as steady.
- The same sample must come out the same on every path: live and history, ingest and backfill, API, export, report, and model input. Disagreement between two in-repo paths on one fixture is the strongest evidence.
- Work from source and in-repo fixtures only. Never connect to a plant system, and stop at the stored row, response field, export cell, or model input, never at a physical consequence.
- Use `confirmed` for a source-complete path plus a bounded fixture run that shows the wrong received result. Use `needs_validation` when the decisive fact is source-system or site configuration outside the repository: timestamp policy, compression settings, device scaling, site time zone, or tag-naming practice.
```

## Acquisition and decoding attack classes (subagent_type: `general`)

**Subscription parameters and item results never read back**
The reader assumes it got the sampling interval, queue size, publishing interval, keep-alive, deadband, and quality of service it asked for, and that every monitored item or subscription was created, while the server revised some and refused others: data arrives far slower than believed, a refused tag never reports and reads as "no change", and a staleness timer shorter than the revised keep-alive fires falsely. Check that each create or subscribe call reads its per-item results and revised values, compares created with requested, stays within the server's per-call limits, and derives its time-outs from the revised values. Check that a percent deadband is set only where the item's range is known, and that deadband and sampling settings are stored with the series. A refused item or revised rate surfaced as a status on the tag is not a defect.

**Sample loss and source freeze inside a live session**
While the connection is up, samples are dropped or the source stops, and the stored series shows nothing: a monitored-item queue overflows and the overflow bit is discarded with the rest of the status code's information bits, a gap in notification or Sparkplug sequence numbers goes unchecked, or a frozen source produces no notifications under a filter that ignores the timestamp, so "no change" and "source dead" look alike. Check that status codes are kept whole, or that overflow, limit, and semantics-changed bits are read before the code is reduced to good or bad; that sequence numbers are tracked through their wrap; and that liveness rests on a heartbeat tag, a periodic read, or a timestamp-triggered filter instead of the time of the last callback. What the store then does with a stale value is **Stale value and liveness misrepresentation**. A detected loss written to the series as a gap or flag is not a defect.

**Reconnect without gap recovery**
After a session or connection loss the reader reconnects, recreates its subscriptions, and carries on, so the outage is a hole with no marker, or values republished from before the outage overwrite newer ones; a client library with no automatic reconnect instead keeps the last values on screen with no error. Check what the code does on loss: transfer or recreate subscriptions, republish or re-read every item, backfill from history, and write a gap marker. Check that node identifiers stored by namespace index are resolved again from the namespace URI on each connect, that a redundant server's service level is read before its data is trusted, and that a watchdog fails when nothing, not even a keep-alive, arrives within the negotiated window. An outage marked in the series is not a defect.

**Register decoding and device error responses read as values**
A multi-register value is assembled with a guessed word or byte order, the wrong sign, width, or address base, or from two reads taken at different moments, and the result is a finite, plausible number; or a device exception, a time-out, or an error object that the library returns instead of raising is indexed or defaulted into zero or the previous buffer. Check that word order, byte order, type, scale, and address base are per-device configuration with no silent default, that each multi-register value comes from one request, that every read result is tested for the library's error state before its data is used, and that one bad address does not zero or drop a whole grouped read unnoticed. The device's true register map is `needs_validation` unless the repository documents it.

**Non-simultaneous reads stamped as one instant**
A polling cycle reads its tags one after another over seconds and stamps them all with the cycle start or collection time, a cycle that overruns its period skips reads without counting them, or a batched read's results are filtered before they are paired with their requests, so values shift to the wrong tags. Check which time each value receives (the device's, the read's, or the cycle's), whether cycle duration is measured against the period, and that results are paired by position before any are dropped. The finding is a calculation that treats the values as one state, such as a balance, a ratio, or a model input, or a stored rate below the configured one with no marker.

**Metric metadata, datatype, and encoding drift**
The reader interprets a payload with metadata it remembered or assumed instead of what the source now declares: a Sparkplug metric's datatype, given only at birth, is kept from an earlier session; a quality property that is present only when quality is not good is never read; every metric is stamped with the payload time instead of its own; a death message from an earlier session marks the current one dead; units and ranges cached at start-up survive a change the server flagged; or a 64-bit count or identifier passes through a double and loses its low digits. Check that per-metric type, quality, and timestamp are taken from the current birth and message, that cached metadata is invalidated on rebirth and on the server's change flags, and that 64-bit integers travel as integers or strings. A reader that rejects a metric it cannot interpret is not a defect.

## Quality, freshness, and time attack classes (subagent_type: `general`)

**Quality-code loss and misclassification**
A sample's quality is dropped, collapsed to a boolean, defaulted to good, or mapped to the wrong severity between source and consumer, so a Bad or Uncertain value reaches a record or decision as valid. Trace each StatusCode, quality byte, or quality string through decoders, mapping tables, schema columns, and serializers; check that severity is read from the two top bits rather than by comparing the whole code with Good or zero, that the reserved severity is treated as Bad, and that unknown or vendor-specific codes fall to a non-good default. Check that a Bad sample's Value field, which carries no usable meaning and which a conforming server sets to null, is never stored, aggregated, or forwarded as a number, and that exceptions, timeouts, and parse failures in the reader produce Bad rather than Uncertain, Good, or the previous value. Compare what each mapping makes of Good_LocalOverride, Uncertain_LastUsableValue, Uncertain_EngineeringUnitsExceeded, Uncertain_SensorNotAccurate, and Uncertain_SubNormal. A collapse is not a defect unless a downstream consumer receives a non-good sample with no quality, or with a better quality than the source sent.

**Stale value and liveness misrepresentation**
A last-known value reaches a consumer as current, with no age, after its source has stopped updating, or a connection indicator reports healthy while no data is arriving. Trace what the stored current value becomes on disconnect, on Bad_NoCommunication or Uncertain_LastUsableValue, on a Sparkplug NDEATH (after which the host must mark that node's metrics stale), and on a reader restart, and whether staleness is computed from source time, server time, or write time. Check whether a cached read returns a best-effort value older than the age requested, and whether retained MQTT messages delivered at subscribe, which Retain As Published 0 forwards with the RETAIN flag cleared, enter the store as fresh samples stamped with arrival time. Check every as-of join, forward-fill, and latest-row query for a maximum age, since without one a value of any age is returned as current. Compare the liveness logic with each source's update behavior: a check that needs per-tag samples flags steady tags falsely, and one that only watches the socket misses a source that is connected but frozen. Silence is not a defect unless a value or health state reaches the consumer with no age or staleness indication that the code had the facts to produce; how a screen shows age belongs in `ALARMS-HMI-AND-DISPLAY.md#Last-known value presented as live`.

**Timestamp source and clock-skew confusion**
Source, server, gateway, and arrival timestamps are chosen inconsistently between paths, substituted silently when one is missing, or trusted or clamped without regard to clock skew, so the same sample is stored or ordered at different times. For each reader, record which timestamp becomes the stored time, what happens when SourceTimestamp is null (a source that cannot stamp leaves it null, and server time is then not data time), and whether live subscription, history read, backfill, and export pick the same one. Check that the reader requests the timestamps it later uses, and that a quality change keeps the time the source recognised it rather than the time the reader noticed it. Trace future stamps and large skews: clamping to now rewrites the time without a flag, trusting them lets a future-stamped sample win last-write-wins and freeze the current value, and dropping them loses data silently. Choosing one timestamp is not a defect unless two paths disagree or the substitution is invisible to the consumer.

**Time-zone, daylight-saving, and epoch-unit errors**
Naive local times are assumed to be UTC, a time-zone conversion is applied twice, the repeated or missing daylight-saving hour is collapsed or invented, or epoch seconds, milliseconds, and 100-nanosecond ticks are mixed, so samples land at the wrong instant. Trace every parse and format of time through file and CSV imports, database column types with and without zone, driver and ORM defaults, query bounds, bucket boundaries, and export writers, and record the zone and unit at each hop. Feed a fixture covering both daylight-saving transitions, with duplicate local times in the fall-back hour, and check that no samples are merged, reordered, or dropped and that local-day buckets on transition days span the hours they claim. Check that epoch fields are scaled by their declared unit, that OPC UA DateTime ticks count from 1601 rather than 1970, and that the minimum and maximum DateTime sentinels are treated as no time rather than stored as real dates. A zone choice is not a defect unless a consumer receives a sample at an instant different from the one the source recorded.

## Units, scaling, and counter attack classes (subagent_type: `general`)

**Engineering-unit loss and double conversion**
A value's unit is dropped, assumed from a default, taken from a stale or wrong mapping, or converted twice, so the consumer reads a number in a unit other than the one labelled or produced. Trace unit metadata from the source (EUInformation, where a unitId of -1 means no unit is available; tag configuration; file headers; lab method) through ingest, storage, conversion, and every output, and check that a missing unit stays missing rather than becoming the site default. Find every conversion site and check whether a value converted at ingest is converted again at query, export, or model-feature time, and whether gauge versus absolute pressure, mass versus volume basis, and percent versus fraction travel with the value. Check what happens to history when a tag's unit changes: rows written before the change must keep their own unit rather than being relabelled with the new one. Free-text unit matching is not a defect unless two spellings resolve to different conversions on a path a consumer uses.

**Raw-count scaling, range clamping, and storage precision loss**
Raw counts, scaled integers, or fixed-point registers reach consumers as engineering values without scaling, with the wrong or a superseded scale, or after clamping and narrowing that hides the true reading. Trace scaling parameters, raw and engineering ranges, offsets, and word and byte order from configuration to the conversion code, and check that the scale applied to a historical row is the one in force when it was written. Check whether out-of-range values are clamped to the engineering range, replaced, or dropped without carrying a quality such as Uncertain_EngineeringUnitsExceeded, so a reading at or beyond a limit looks like a valid in-range value. Compare source data types with storage and transport types: 32-bit floats, integer columns, fixed decimal places, JSON number handling, and spreadsheet exports can round, truncate, or overflow large totals, high-resolution values, and 64-bit identifiers. Precision loss is not a defect unless the lost digits change a value that a decision, limit check, or record depends on.

**Counter and totalizer reset and rollover errors**
Rates, consumptions, and production totals computed from counters or totalizers go wrong across a rollover at the counter's width, a manual or batch reset, a device replacement, or a restart that re-zeroes the count. Find every difference, rate, and period total computed over counter tags, and check that the code knows each counter's width or maximum, distinguishes a wrap from a reset from a negative step caused by a bad sample, and excludes or flags the interval that spans one. Check that differences are taken per source before sources are summed, since after a sum one source's reset can no longer be told from a drop in the total, and that per-window increases are computed from bounding samples so they add up to the total. Check that a reset inside an aggregation bucket neither produces a large spurious spike nor silently loses the pre-reset portion, and that interpolating or forward-filling a counter across a gap does not invent or hide consumption. A counter discontinuity is not a defect unless a computed rate or total delivered to a consumer is wrong without a flag.

**Unit symbol, quantity-kind, and offset conversion errors**
A unit string is matched after case folding, so milli and mega or metre and molar collapse; a conversion lookup that finds no entry falls back to a factor of one; a temperature difference is converted with the offset of a temperature; or a percentage, fraction, or parts-per value is compared with another on a different basis (mass, volume, or mole) because the basis is stored nowhere. Check unit normalisation for case changes and alias tables, conversion functions for a default factor and for mass-to-volume conversion without a stated density, temperature conversion for a separate path for intervals, and schemas for a quantity-kind or basis field beside the unit. A conversion that refuses an unknown or mismatched unit is not a defect.

**Non-finite and sentinel value handling**
NaN, infinity, or a device's failure code or out-of-band signal travels as an ordinary number, or is turned into zero or null on the way: a current-loop input outside its valid band is scaled into a reading just beyond range, a sentinel such as -9999 or the type's maximum enters an average, a NaN makes every limit comparison false so the value passes as within limits, sorts as the maximum, or is serialized as invalid JSON that a client reads as null or zero. Trace where non-finite values and documented failure codes are detected, check that each becomes a Bad or missing sample with a reason at the first hop, and check limit tests, sorts, maxima, and serializers for what they do with any that remain. The failure bands and codes of a particular device are `needs_validation` unless the repository's device configuration states them. A non-finite value stored as explicitly missing, with its quality, is not a defect.

## Aggregation, interpolation, and gap attack classes (subagent_type: `general`)

**Interpolation across gaps and stepped signals**
Interpolated, resampled, or as-of values are computed across a gap, a Bad region, or a stepped signal as if the signal were continuous and sloped, so the consumer receives values the source never produced. Trace every interpolation, resample, as-of join, and fixed-interval grid: check the maximum gap it will bridge, whether Bad and Uncertain samples serve as endpoints, and whether a Stepped property or a discrete, setpoint, mode, state, or counter type switches the code to hold-last-value instead of linear interpolation. Check that history reads request bounding values when a calculation needs values at the window edges, that bounding samples, which count toward the per-node value limit, are not mistaken for in-window data, and that a read capped at its maximum values per node is not treated as the complete window. Linear interpolation of a continuous analog signal across a short gap is not a defect unless it bridges a period the source marked Bad or missing and the output carries no flag.

**Aggregate quality and weighting contamination**
Averages, minima, maxima, totals, and statistics include Bad or Uncertain samples, the meaningless values of Bad samples, or filler values, or weight irregular samples by count instead of by time, so an aggregate looks valid while its inputs were not. Read each aggregation function, database continuous aggregate, and in-code rollup, and check which qualities it admits, whether a result built from partly bad input carries a non-good quality, and whether PercentDataGood, PercentDataBad, and TreatUncertainAsBad are set, passed through, or silently defaulted. Compare time-weighted and sample-weighted averages on a report-by-exception fixture, where a sample-weighted mean overweights periods of rapid change. Check that each aggregate carries the count or covered fraction of its window and applies a minimum-coverage rule: most libraries skip missing values, so one sample yields a normal-looking mean and an empty window sums to zero. Check that every path producing the same named aggregate, such as API, export, scheduled report, and model feature, applies the same quality rule and weighting. Sample weighting of strictly periodic data is not a defect.

**Window boundary, bucket origin, and label errors**
A sample on a window edge is counted in two adjacent windows or in none because both bounds are inclusive or two components use different conventions; buckets are aligned to UTC midnight or an arbitrary origin instead of the period the output names; or a bucket is labelled by its start in one component and by its end in another, so joined series are shifted by one period. Check time filters for half-open bounds that tile, bucket functions for an explicit zone and origin, and every resample and window aggregate for a stated closed side and label; compare two components' output for a sample placed exactly on a boundary. Production-day and shift calendars belong to `MODELS-BATCH-AND-SIMULATION.md#Production-day and shift boundary errors`. One stated convention applied on every path is not a defect.

**Compression and deadband misreading**
Values stored under compression, exception deadbands, or report-by-exception are read back as missing data, as gaps, or as the true resolution of the signal, so consumers see outages that were steady periods or precision the store never kept. Find where deadband and compression settings live and whether readers know them; check that an absent sample during a steady period is reconstructed as held or interpolated by the store's rule, not flagged as a gap or counted as zero, and that a true outage stays distinguishable from a quiet signal. Check that analyses, models, and change detection do not treat stored points as the full sampling rate, read a flat stored line as zero variance, or report a change smaller than the deadband as real or as absent. Compression itself is not a defect; the defect is a reader that interprets its output as something the source did not produce, and when the settings live in a historian outside the repository the candidate is `needs_validation`.

**Gap filling, zero substitution, and silent row loss**
Missing, null, or Bad samples become zero, the previous value, an interpolated value, or no row at all somewhere between store and consumer, and nothing tells the consumer which values are real. Trace null handling in schemas and column defaults, dataframe resample and fill calls, SQL `COALESCE` and default values, serializers that omit nulls or write empty strings, CSV and spreadsheet exports, and model feature pipelines. Check that zero is never the missing marker for a signal where zero is a valid reading, that forward-fill carries a fill flag or a limit, that filters dropping bad or unparseable rows report how many they dropped, and that exports and reports cut at a row, page, or file-size limit say so. Rendering of gaps on screens and trends belongs in `ALARMS-HMI-AND-DISPLAY.md`; this class covers stored, delivered, and computed values. A documented fill that the output marks is not a defect.

**Calculated value formula and input-version drift**
A calculated or reported value, such as a yield, mass balance, efficiency, soft-sensor estimate, or report total, is stored without the formula version and input revisions that produced it, so a later formula change or input correction silently changes historic values or leaves them impossible to reproduce. Find where each calculation is versioned, whether stored results carry that version and their input references, and whether history reads or reopened reports recompute with the current formula, so a report a person sent or signed shows different numbers later. Apply the same check to validation schemas, data contracts, and mapping revisions: a published version edited in place, or rows with no stamp of the version they were validated or mapped under, lets history be judged by a rule it was not written under. Check that a recalculation is recorded as a new revision or flagged on the values it changed, and use `RECORDS-AUDIT-AND-SIGNATURES.md#Signature-to-record-version binding gaps` when the changed content was signed. Computing on read with the current formula is not a defect unless the result is presented as what was reported, recorded, or signed at an earlier time.

## History writes and tag identity attack classes (subagent_type: `general`)

**Late and corrected sample write-rule conflicts**
Late, backfilled, or corrected samples overwrite good data, are discarded, or are accepted by one write path and rejected by another, so stored history depends on arrival order and path rather than on what the source produced. For each writer, such as live ingest, store-and-forward flush, backfill import, manual correction, and replay, record the uniqueness key and the conflict rule: insert-ignore, upsert, last-write-wins by arrival, or last-write-wins by source time. Check that the rules agree, that a buffered flush after an outage neither drops nor duplicates the buffered window, and that aggregates, current-value tables, and caches are recomputed or flagged when a late sample lands in a closed bucket. Check that a correction rewrites every field of the stored point where the store merges fields on a duplicate key, that every backfill path refreshes the rollups over the range it touched, that no retention rule removes raw rows a rollup still depends on, and that a rollup joined to a tag or unit table is rebuilt when that table changes. Check that a corrected value stays distinguishable from an original one; who changed what, and the audit trail, belong in `RECORDS-AUDIT-AND-SIGNATURES.md`. A deliberate overwrite rule is not a defect unless two paths apply different rules to the same key or an accepted late sample leaves a stale derived value.

**Reconnect, replay, and history-into-live duplication**
Reconnects, session resumption, store-and-forward replay, and history reads produce duplicate samples or fold historical values into a live stream, so totals double, current values move backward, or an old value is presented as the newest. Check how the uniqueness key handles a sample redelivered after reconnect (MQTT QoS 1 delivers at least once), a subscription that resends the current value on resubscribe, and a replayed buffer whose stamps overlap stored rows. Trace historical data that arrives on a live channel, such as Sparkplug metrics flagged `is_historical`, which the chronological-order rule for live metrics does not cover, or a backfill pushed through the live writer, and check that it never updates the current value or triggers live-only logic. Ordering and duplicate delivery as security concerns belong in `PROTOCOLS-RPC-AND-MESSAGING.md`; this class covers stored and delivered values. A duplicate is not a defect unless it changes a row count, aggregate, total, or current value a consumer reads.

**Ingest checkpoint and store-and-forward spool loss**
The cursor that records how far an incremental load has read, or the on-disk buffer that holds samples during an outage, is lost, reset, corrupted, or overflowed, and the pipeline resumes as if nothing happened, leaving a gap, a replayed window, or reordered samples in the store. Find where each checkpoint, offset, or last-read timestamp is kept and when it advances relative to the durable write, and trace what a missing, unparseable, future-dated, or older-than-retention checkpoint does on restart: full reload, resume from now, or resume from zero. For each spool, read its size and age limits, its overflow policy (drop oldest, drop newest, or block), and its drain order, and check that every dropped or skipped window is counted, logged, and marked in the data instead of reading as a quiet signal. A checkpoint or spool that a lower-trust local account can read or rewrite is a `security` candidate for `DESKTOP-MOBILE-AND-LOCAL-IPC.md`. A bounded buffer is not a defect unless samples it drops or reorders reach the store or a consumer with no marker.

**Tag identity drift and name reuse**
A tag rename, a reused name, an alias reassigned at rebirth, or a mapping table that differs between sites or revisions makes history, current values, units, or limits join the wrong signal. Find every place an identity is formed, such as tag path, node id, display name, Sparkplug metric name or alias, asset path, and mapping row, and check which one keys stored history and which one later reads join on. Check that a renamed tag keeps its history, that a reused name does not inherit the old signal's history, limits, units, or quality rules, and that Sparkplug aliases are rebound from each birth, with an undefined alias rejected or answered with a rebirth request rather than guessed. Compare mapping tables across sites, revisions, and import paths for one key resolving to different signals, and check that an effective date or revision exists where mappings change over time; how site copies of a mapping drift apart is `GOVERNANCE-CONFIGURATION-AND-CHANGE.md`, while the wrong join it produces is here. A rename is not a defect unless a read joins samples from two different signals, or loses one, without the consumer being told.

## Lab, sample, and specification data attack classes (subagent_type: `general`)

**Lab sample, result, and entry time confusion**
Lab and manual results are stored or joined at the result, approval, or entry time instead of the sample time, or the reverse, so a result is aligned with the wrong process conditions. Trace sample-drawn, received, analysed, approved, and entered times from the lab import, file, or form to storage, and check which one keys the row, which one joins to process history, and whether a missing sample time is filled with entry time without a flag. Check how reruns, retests, amended results, and several results for one sample are keyed, so that a retest neither overwrites the original silently nor appears as a second independent sample. Check zone handling for times typed by people and for instrument exports, which can carry local time with no offset, and check that a time a person types for when an activity happened is stored beside a server-captured entry time that reaches the record view and export, so a late entry cannot read as contemporaneous. Storing one time is not a defect unless a consumer aligning, trending, or releasing on the result receives a time other than the one the field implies.

**Censored, text, and specification-limit coercion**
Text results such as "<0.5", ">100", "ND", "N/A", or a comment become numbers, zero, null, or a parse failure, and specification limits are stored without the unit, method, or version they belong to. Trace result parsing in imports and forms: check that a censored result keeps its qualifier and limit instead of becoming the limit value, half of it, or zero, that non-numeric results are neither dropped nor coerced, and that decimal commas and thousands separators parse as the source locale intended. Check that sums, averages, trends, and training sets built over results report how many were censored instead of counting each at its limit or leaving it out. Check that specification and control limits carry a unit, a product or grade, and an effective date or version, and that each result is compared with the limit in force at its sample time, not the current one. A pass, fail, or trend computed from a coerced result or a mismatched limit version and delivered without a flag is the finding; a stored text value the consumer sees as text is not.

**Result-to-limit comparison and rounding errors**
A result is compared with a specification or control limit after rounding by a rule nobody chose, or unrounded where the specification rounds first; with binary floating point or round-half-to-even where the stated rule is round-half-up; with an inclusive test where the limit is exclusive; against an open-ended limit stored as zero or a large sentinel; or after being rounded for display, stored, and rounded again. Check where each limit's rounding method, digits, and inclusivity are stored, that one function makes every pass or fail comparison in decimal arithmetic, that an absent bound is null, and that the raw result is kept apart from its displayed form. Run a result exactly at a limit and one that differs only beyond the reported digit. A decision rule the software does not claim to apply is not a finding; two paths that return different verdicts for one result and limit is.

**Unverified, retracted, and replicate result use**
A report, release check, trend, or model reads every result row or the newest one, whatever its state, so a preliminary, rejected, or retracted result is used as final; a retest inherits the original's value or time; replicates are averaged so a failing one disappears, or one is excluded with no recorded reason; or results produced beside a failed control sample or on an instrument marked out of calibration carry no mark. Check each consumer's query for a status predicate, how a retest links to its original, whether per-replicate values and exclusions are kept, and whether a result carries the method, instrument, and control state it was produced under. Who may verify or retract belongs to `RECORDS-AUDIT-AND-SIGNATURES.md`. A consumer that shows each result's state beside it is not a defect.

## Universal moves (apply across the above)

- Build a small fixture series per signal type containing a Bad sample with a non-null value, an Uncertain sample, a null SourceTimestamp, a gap, a steady compressed period, a duplicate, a late sample, both daylight-saving transitions, a counter wrap and a reset, an out-of-range reading, a NaN, a device error response, a sample exactly on a window edge, a censored lab result, and a renamed tag. Push it through every in-repo path to every output, without connecting to any plant system.
- For each signal, tabulate value, timestamp, unit, quality, and identity at each hop: source, decoder, mapping, store, query, aggregate, export, and model feature. The first hop where an attribute changes or disappears without a visible marker is the candidate.
- Compare paths that should agree: live and history read, live and backfill, API, export, report, and model input, and one site's or revision's mapping against another's. Two in-repo paths disagreeing on the same fixture is direct evidence.
- Grep for the idioms that cause these defects: fill-with-zero and `COALESCE(x, 0)`, `or 0` and `?? 0` defaults, quality defaulting to good, stamping with the local clock, repeated zone conversion, `* 1000` and `/ 1000` on times, `float32` and integer casts on values, `min`/`max` clamps on readings, as-of joins and forward-fills with no tolerance or limit, sums and means with no count beside them, `BETWEEN` on timestamps, coerced numeric and date parsing, case-folded unit strings, and `round(` on results compared with limits.
- Build a condition table for each output: what it delivers when an input is Bad, stale, missing, late, duplicated, out of range, or not yet present. Any row where the honest answer is "unknown" and the output is a normal-looking value is a candidate.
- Run time checks under an explicit non-UTC zone with daylight saving and a pinned clock. A test that passes only because the sandbox runs in UTC proves nothing.

## Validation rules (apply before reporting ANY finding here)

1. Name the source sample with its value, timestamp, unit, quality, and identity; every transformation; the destination; the consumer; the decision it informs; and the ordinary plant condition that triggers the difference.
2. Show that the received result differs from what the source produced and that the difference is invisible, or flagged misleadingly, at the destination. Check every field, column, header, API attribute, and documented convention through which the consumer could see quality, age, unit, fill, or revision.
