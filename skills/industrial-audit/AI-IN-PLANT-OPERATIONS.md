# AI in Plant Operations Hunting

#### When to use this file

Reach for this file when the target lets a model or agent read plant data or act in a plant: assistants over historian, alarm, batch, maintenance, or laboratory data; agents whose tools reach MES, ERP, maintenance, recipe, or OPC UA paths; models whose output becomes a work order, shift note, investigation record, forecast tag, or approval card; and fine-tuning, embedding, or evaluation pipelines fed with plant data. The important data path is *plant source → tool result or retrieval → model → display, record, or plant-facing action*. Always use this file with `AI-AND-LLM.md`, which owns injection, context bleed, memory poisoning, agency, approval binding, MCP trust, and output rendering; this file adds only what plant data and plant actions change. Use `PROCESS-DATA-INTEGRITY.md` for the acquisition and storage pipeline before data reaches the model, `ALARMS-HMI-AND-DISPLAY.md` for how values and alarms are rendered, and `CLOUD-AND-DEPLOYMENT.md` for provider and network configuration. The classes here produce both `security` findings (write reach, approval bypass, an ignored disable switch or autonomy level, egress, provider routing, retention, cross-site leakage) and `data_integrity` findings (fabricated or degraded grounding, unit and time errors, provenance gaps, unfounded labels, silent fallback).

Split large targets by agent authority, action path, grounding path, record path, and data boundary.

## Core discipline (include in every agent prompt for this domain)

```
- Model output is a proposal, never a measurement. Trace every tag, value, unit, and timestamp the model emits back to the tool result or record it claims, and find the code that checks it.
- The software's own claims set the boundary: recommend-only, human approval, read-only, push-only, on-premises, a named provider or region, a stated retention, AI switched off for a site, no training on customer data. A finding is code that contradicts such a claim or exceeds the requester's authority, not a missing best practice.
- Count only deterministic controls that run after the payload is final and before the side effect: server-side approval records, allowlists, state re-reads, expiry checks. A system prompt telling the model to ask first is not a control.
- Never connect to a live plant system, send a write or command, or reason about physical consequence. Stop at the payload, record, display state, or outbound request the software produces, and stand in for the model with a scripted stub.
- Name the kind: `security` when a principal gains reach, authority, or data across a boundary; `data_integrity` when a value, time, unit, quality, identity, or record state reaches a person, record, or action differently from the source with no visible indication.
- Return `confirmed` only with a source-complete path from plant source or model output to the sink plus a bounded local check on recorded fixtures and model stubs. Use `needs_validation` for provider behaviour, deployment topology, downstream system configuration, and model behaviour not observable locally. Any path into an interlock, trip, or other safety function is always `needs_validation`, with the safety system's owner named.
```

## Agent authority and autonomy attack classes (subagent_type: `general`)

**Agent approval, signature, and release reach**
An agent can complete the approval, signature, release, acknowledgement, or management-of-change step for an action it proposed, or the proposal records the agent or a system account as requester, so a requester-versus-approver check passes when the person who prompted the agent also approves. List every approve, sign, release, and close route that the agent's credential or the user's forwarded session can reach, and check on the server whether those routes refuse calls from an agent run and whether one agent or automation can approve another's proposal. Check how the requester of an AI-drafted change is stored and whether the separation check compares the approver with the person who prompted or owns the run. Use `RECORDS-AUDIT-AND-SIGNATURES.md#Signature replay and re-authentication gaps` for signing without fresh credential entry; a person approving the exact payload of their own agent's draft is intended authority unless the software separates requester and approver.

**Agent reach into authority and permission settings**
An agent tool, automation step, or generated configuration can create or change users, roles, group memberships, site grants, writable-point allowlists, approval rules, tool-enable switches, or the agent's own scopes, so a prompt, a retrieved document, or a lower-authority requester can widen what the agent or a person may do. Map each tool, including generic file, settings, and record-edit tools, to the authority settings it can write, and check on the server that each change requires the requester to hold that authority and produces the same approval and audit entry as the same change made by a person. Check whether the agent can turn on a tool, folder, or write switch that an administrator left off, or remove a blocked path that narrows its own reach. Use `OT-BOUNDARY-AND-CONTROL-WRITES.md#Writable-point allowlist matching and ownership gaps` for how allowlist entries match; a tool that only proposes an authority change for an administrator to approve on the exact payload is not a defect.

**AI disable switch and autonomy-mode enforcement gaps**
The software offers a setting that turns AI off for a site, tenant, or user, or an autonomy level such as suggest-only, draft, or act-with-approval, but the setting is read in the client, written into the prompt, or checked on the chat route alone, so other paths still call the model or act above the configured level. List every model call path and every action dispatcher, including scheduled jobs, automations, background summarizers, plugins, MCP endpoints, webhooks, and retries, and find where each reads the switch or level and from which store. Check that a site-level setting cannot be overridden by a user preference, request field, or tool argument, that the stricter of site and global values wins, and that turning AI off stops queued and in-flight runs. Report plant data sent to a model, or an action taken, on a path the setting says is off; a product that offers no such switch or level has a missing feature, not a defect.

## Recommendation-to-action attack classes (subagent_type: `general`)

**AI recommendation-to-action bypass**
A model suggestion can reach a setpoint write, command, recipe change, work order, batch step, or record entry without the human approval the software claims for AI-originated actions. Enumerate every path from model output to a side effect: direct tool handlers, automation and scheduled runners, bulk or "apply all" endpoints, retry and resume queues, and the API routes each client calls. Verify that each path requires a server-side approval record created by a person and bound to the final payload, as in `AI-AND-LLM.md#Action-confirmation and approval binding`, rather than a client-side dialog or a flag the model or tool can set. A recommend-only feature with no reachable write path, or an action the requester intentionally performs through the normal product interface, is not a defect.

**Approval not re-checked against current process state**
An approval granted against a snapshot of process state executes after that state changed, so the mode, value, limit, batch phase, equipment status, or permit that the approval card displayed is no longer true. Find what the card showed as the basis for the action, then check whether execution re-reads those values, compares them with the approved snapshot, and refuses or re-prompts on difference or expiry. Check queued, scheduled, retried, and offline-resumed executions, where the gap between approval and execution is longest. This is a defect only when the card presents state as the basis or the software states an expiry or re-check rule; an approval documented as unconditional is a design choice, and expiry, replay, and single use of an approved control write belong to `OT-BOUNDARY-AND-CONTROL-WRITES.md#Approved-write staleness, expiry, and replay`.

**Approval card built from model narrative**
The approval card, confirmation summary, or notification shows the model's description of the action rather than a rendering of the payload that will execute, so tag, value, unit, target system, or scope can differ from what the approver read. Trace each card field to its source: model prose, a model-written summary field, or the normalized tool-call object the handler will use. Compare the card with the executed payload for unit conversions, tag aliases, resolved asset identifiers, batch membership, and defaults the handler fills in. A card rendered from the final normalized payload, with model prose shown separately and labelled, is not a defect.

**Indirect plant write reach through connected systems**
An agent tool that writes only to a business or engineering system still reaches the plant because that system pushes onward to control: an MES recipe or parameter table, a batch procedure, a maintenance order that records a bypass or override, an ERP order released to the floor, or a gateway mapping from a field to a tag. Map each agent tool to the system and fields it writes, then trace the onward path as `OT-BOUNDARY-AND-CONTROL-WRITES.md#Indirect write-down through an intermediate system` describes. Compare that reach with the software's own claims for the agent, such as read-only or recommend-only operation, and with the requester's authority in the downstream system, and check whether the tool description and approval card tell the approver that the write continues to the plant. A write that stays in the business system is not a plant write, and onward behaviour configured outside the repository is `needs_validation` with the downstream system's owner named.

**Generated plant logic and configuration promotion**
Model-generated control logic, scripts, alarm limits, historian calculations, gateway or OPC UA server configuration, or recipe parameters can be saved, exported, or deployed into an artifact a plant system loads, without the engineering review the software applies to the same artifact written by a person. Trace generated content from model output to file, store, or export endpoint, and check for review state, author attribution, a diff against the current version, and a promotion gate that neither the model nor a tool can set. Treat generated configuration the software itself loads and acts on, such as polling lists or automation definitions, as a tool-argument sink under `AI-AND-LLM.md#Tool-argument injection into a downstream sink`, and generated allowlists or permission settings under **Agent reach into authority and permission settings**. Code shown for a person to copy, or a draft that no API can move out of review, is not a defect.

## Grounding and fabrication attack classes (subagent_type: `general`)

**Fabricated tag, value, and citation acceptance**
Model output names a tag, asset, document, or sample that does not exist, or quotes a value, time, or unit the cited data does not contain, and the software shows it as fact or stores it in a record without checking it against the source. Find the post-processing between model output and display or storage: resolution of tag references against the tag directory, comparison of quoted numbers with the tool results in the same trace, and whether citation fields are filled from model text or from retrieval metadata. Check structured outputs too, where a model-filled tag identifier, value, or quoted excerpt is trusted because it parsed. Free text visibly labelled as model output, with no stored claim and no citation styling, is not a defect; a citation or value field that looks verified is.

**Grounding context stripped of quality, time, or unit**
Tool results, retrieval chunks, or prompt context drop the quality, timestamp, unit, or site the source carried, so the model grounds on stale, Bad or Uncertain, substituted, or interpolated values as if they were current and good. Read the serializers that turn historian, OPC UA, laboratory, and alarm data into tool results and prompt text, and check that an Uncertain or Bad StatusCode, a null SourceTimestamp, a cached best-effort read, a manually entered or substituted value, and the engineering unit survive into what the model sees. Check aggregates and summaries built for the model, where averaging across Bad regions or reporting a last value without its age hides the problem. Use `PROCESS-DATA-INTEGRITY.md` for defects in the acquisition and storage pipeline; this class covers only the hop from stored data into model context.

**Model unit and time-zone confusion**
Unit or time meaning is lost between the model and its tools: a time range the model writes is read in the server's zone instead of the plant's, a naive timestamp is assumed UTC or local, a relative window resolves against the wrong clock, or a value travels without its unit and a handler default applies. Read each tool schema and handler for explicit time-zone and unit fields, default zones, daylight-saving transitions, and parsing of the formats a model is likely to emit, then follow model-produced values into queries, writes, records, and displays. Compare the unit a handler assumes with the tag's configured engineering unit, and the time a record stores with the time the person asked about. A tool that rejects ambiguous input, or echoes the resolved range and unit to the person before use, is not a defect.

**Cross-site tag and asset resolution in grounding**
Grounding resolves a tag, asset, or document by name across sites, units, or plant models, so the model reasons over another site's point with the same name, or over the history of a renamed or retired tag. Check name-to-identifier resolution in tools and retrieval for site and plant scope, alias and rename tables, effective dates, and the behaviour when a name matches more than one point. Verify that the resolved site and point identity reach the answer and any record it creates. Within one customer this is `data_integrity`; across customers or tenants it is the access-control defect in `AI-AND-LLM.md#Cross-session or cross-tenant context bleed`.

## Records, change control, and presentation attack classes (subagent_type: `general`)

**AI provenance gaps in plant records**
Records the AI helps create, such as work orders, shift notes, investigation reports, deviation entries, recipe changes, and approvals, omit the model, prompt, tool versions, and input data that produced them, or log the AI's contribution under the human user's identity. Read the record schema and write path for a model identifier, prompt or configuration version, tool versions, input references with their timestamps, and an actor field that separates the AI from the person who approved. Logging content the AI wrote or changed as a person's entry is a misattributed audit-trail entry when the person did not review that exact content before it was saved, or when the software states that it separates AI and human actions. Check that model-written content saved back into a memory, example, or retrieval store keeps an origin marker that ingestion honours, so later answers do not cite model output as a plant record or a person's entry. Missing versions are a defect when the software presents the record as traceable or reproducible, or when the record enters a regulated or release path; chat transcripts that never become records are not.

**Model, prompt, and tool change outside change control**
A model swap, retraining, prompt edit, tool-definition change, retrieval-index rebuild, or change of model provider or endpoint alters what the AI recommends or records, or where plant data is processed, without the review, approval, and versioning the software applies to other plant configuration such as alarm limits, recipes, or calculations. Check how the model is selected (a pinned version or a moving alias), where prompts, tool descriptions, and provider endpoints load from, including remotely fetched settings, and who may edit them, whether retraining promotes a model automatically, and whether drift or performance checks gate promotion. Verify that each change is recorded with its effective time so later outputs can be tied to it. A deployment with no change control for any configuration is ordinary governance, not this class; the defect is AI configuration exempt from controls the same software enforces elsewhere, or changeable by a principal who cannot change comparable configuration.

**Unfounded confidence and measurement-styled inference**
The software shows a confidence, probability, accuracy, "verified", or "grounded" label that no code computes from evidence, or writes a model estimate, forecast, or inferred value into a tag, trend, or record with nothing that marks it as inferred. Trace each label to its source: a calibrated score, a deterministic check such as comparison with the source record, or text the model wrote about itself. Check whether inferred values written to tags, trends, or records carry a source or quality marker that distinguishes them from instrument data, and whether that marker survives export and downstream reads. Use `ALARMS-HMI-AND-DISPLAY.md#Modeled values styled as measurements` for how a marked value is styled on each surface; the defect here is a label with no basis in code or an inferred value stored with no marker.

**Silent fallback when the model is unavailable**
When the model, provider, embedding service, or a tool fails, times out, or hits a quota, the software returns a default answer, an earlier cached answer as current, an empty result rendered as "no issues found", an unlabelled rule-based answer, or an automatic approval, instead of a visible failure. Read the error handlers in the model client, tool dispatcher, retry wrappers, cache layers, and approval timeouts, and check what reaches the person, the record, and any automation. Verify that a cached or fallback answer carries its age and origin and that a timeout never resolves an approval as granted. A labelled reversion to manual or non-AI operation is the intended failsafe, not a defect; a reroute to another provider or region belongs to **Model provider routing, residency, and fallback drift**.

## Data boundary and safety attack classes (subagent_type: `general`)

**OT data pull and egress beyond the stated boundary**
The AI service pulls OT data through persistent inbound access into the plant network, or sends plant data, engineering configuration, or prompts containing them to a lower-trust zone or third-party provider, while the software claims push-only transfer, on-premises operation, or no egress. Find every outbound client in the AI pipeline, including model providers, embedding and reranking services, tracing and evaluation exporters, error reporters, telemetry, and feedback submissions, and check which still run, and with what payload, under an on-premises or local-model setting. For each OT data source, establish whether the AI side holds credentials and opens connections into OT or receives data that is pushed or brokered out. Where the software states that secrets, personal data, or site identifiers are masked before a provider call, check that every assembly path, including tool results, retrieval, scheduled summaries, and retries, passes through that step. A contradiction of the product's own stated mode is `security`, and network placement and firewall policy outside the repository are `needs_validation`; a tool that connects to a host a tool argument or retrieved content names belongs to `INDUSTRIAL-PROTOCOLS-AND-DEVICES.md#Caller-chosen plant connection targets`, and outbound clients outside the AI pipeline to `OT-BOUNDARY-AND-CONTROL-WRITES.md#Undeclared egress and proxy routing`.

**Cross-site learning-set and embedding leakage**
Plant data from one site or customer enters a fine-tuning set, embedding index, semantic cache, few-shot example store, or evaluation set that serves another, or enters training or evaluation at all when the customer's data-use setting or the software's own stated policy forbids it. Read the pipelines that assemble these sets for tenant and site filters, opt-out settings read at assembly time, and deletion propagation when a customer leaves. Check cache keys and example stores for site scope, and whether evaluation fixtures copied from production keep customer identifiers. This builds on `AI-AND-LLM.md#Cross-session or cross-tenant context bleed`: a forbidden row in an assembled set is confirmable from source, while whether a trained model reproduces it is `needs_validation`.

**Model provider routing, residency, and fallback drift**
A request carrying plant data goes to a model provider, region, or endpoint other than the one the site configured or the software states: a fallback list tried on error or quota, a shared default used when the customer's own endpoint fails, cross-region inference when the regional model is unavailable, or a provider address taken from a user-editable setting. Read the provider and region selector and every retry, failover, and load-balancing wrapper around it, and list each destination a request can reach and the condition that selects it. Check that a residency or own-endpoint setting fails closed with a visible error, that a cross-region or third-party fallback needs a stored administrator opt-in, and that embedding, reranking, and moderation calls follow the same routing as chat. Observe the next destination chosen with a stub provider that returns errors. A fallback the software documents and an administrator enabled is not a defect, and what a provider does with a request it accepts is `needs_validation`.

**Prompt, trace, and derived-store retention overrun**
Prompts, tool results, and model responses holding plant data persist in conversation stores, logs, traces, evaluation sets, review queues, embeddings, or semantic caches longer than the retention the software states, or survive deletion of the conversation, document, user, or site they came from. List every store the AI pipeline writes, including trace exporters, prompt logs, vector indexes, caches, example stores, and their backups, with the time-to-live and purge job of each. Trace each delete and offboarding handler and check that it reaches every derived store instead of the primary row alone, and that a failed purge is visible. Report `security` when a later reader, such as another user, site, or support role, can retrieve content the software says was deleted or expired; use `DATA-ISOLATION-AND-LIFECYCLE.md#Retention and queued-work overrun` for stores outside the AI pipeline. Retention the software never states is not a finding, and provider-side retention is `needs_validation`.

**Model output in safety-function paths**
Model output can feed an interlock, trip, permissive, safety-function bypass, safety setpoint, or the configuration of any of these, directly or through a record or system that another component reads. Trace the path from source only as far as the payload or record the software produces, and never assess the safety function itself. Report every such path as `needs_validation` with the safety system's owner named, never as a confirmed finding about physical behaviour. Reading safety-system status for display only is not in this class.

## Universal moves (apply across the above)

- Draw four maps first: every path from model output to a side effect, every path from a plant source into model context, every record or display that stores or shows model output, and every provider, exporter, and store the AI pipeline sends to or writes. Mark each claim the software makes (recommend-only, approval, read-only, push-only, provider and region, retention, AI off, no training) at the boundary it governs.
- Replace the model with a scripted stub that emits the worst plausible output: a nonexistent tag, a misquoted value, a naive timestamp, a wrong unit, an action with no approval. Observe only the software's deterministic checks, which needs no provider quota.
- Feed a recorded fixture with an Uncertain value, a null or old timestamp, a unit mismatch, and one tag name shared by two sites through each tool serializer, and compare what the model would see with the source.
- Compare direct, scheduled, retried, resumed, bulk, and offline paths for every AI-originated action, and compare normal operation with model failure, timeout, and quota exhaustion.

## Validation rules (apply before reporting ANY finding here)

1. Name the path end to end: plant source or model output, each transformation, the sink (write, record, display, or outbound request), the consumer, and the claim or authority the result contradicts.
2. For action-path claims, show the payload that would execute, the approval or state check that is missing or bypassed, and that the shipped code reaches the sink. Stop at a stub sink or shipped fixture server and send no write beyond the single dummy message needed to show the path exists.
3. For fabrication and grounding claims, cite both the source record and the model-visible or stored value that differs, and show that no check between them catches the difference. A scripted model stub may stand in for model behaviour.
4. For provenance and change-control claims, show the record or configuration that lacks the version or actor, and the comparable control the same software enforces elsewhere or the claim it makes.
5. For switch, autonomy-level, egress, routing, retention, and leakage claims, show the model call, action, outbound payload, chosen destination, surviving copy, or assembled set and the setting or claim it contradicts. Network placement, provider retention, and model memorization outside the repository are `needs_validation`.
6. Return `confirmed` only with a complete source trace and a bounded local result on fixtures and model stubs. Return `needs_validation` with the exact provider, deployment, downstream-system, or model-behaviour fact required, naming the safety system's owner for any safety-function path.
